# DHT20 软件 I2C 接入设计分析

## 1. 文档目的

本文档基于以下资料，提炼 DHT20 接入当前 `stm32f4_DMA_UART_ring_RTOS` 项目时真正需要落地的内容：

- `00_Doc/00_项目需求/项目需求说明书.md`
- `00_Doc/00_项目需求/最终功能需求.md`
- `00_Doc/04_Agent/architecture.md`
- `00_Doc/04_Agent/requirements.md`
- `DHT20产品规格书(中文版) A3-202409.md` / 对应 PDF，版本 V1.3，2024.09

当前目标不是实现通用 I2C 框架，而是使用 STM32F411 的 GPIO 模拟一条软件 I2C 总线，完成 DHT20 温度和相对湿度的可靠读取，并接入现有 FreeRTOS、UART DMA、RingBuffer、RTT/EasyLogger 数据链路。

## 2. 与本项目直接相关的结论

| 项目 | 当前约束 |
| --- | --- |
| MCU | STM32F411 |
| DHT20 总线 | 软件 I2C，不启用 STM32 硬件 I2C |
| SCL | PB6，开漏输出，无内部上拉 |
| SDA | PB7，开漏输出，无内部上拉 |
| 上拉 | 传感器模块提供外部上拉；应确认上拉到 3.3 V |
| DHT20 地址 | 手册按 8 位地址表示：写 `0x70`，读 `0x71`；7 位地址为 `0x38` |
| 采集周期 | RUNNING 状态每 5 s 一次；STOPPED 不周期采集 |
| 单次采集 | STOPPED 状态下由按键双击或 UART `ONCE` 触发 |
| 访问上下文 | 第一阶段由单一采集执行上下文串行访问 DHT20 和 MPU6050 |
| 上层输出 | 通过已有 UART Service -> UART DMA TX 链路发送，不另建发送通道 |

最重要的架构边界是：

```text
APP / Sensor Service
        -> DHT20 设备协议
        -> Software I2C
        -> Platform GPIO
        -> STM32 GPIO Impl
        -> PB6 / PB7 / 外部上拉
```

软件 I2C 只处理总线事务，不处理 DHT20 温湿度业务；DHT20 驱动只处理设备命令、数据帧、CRC 和换算，不处理 START/STOP 业务状态机、LED 或 UART 发送。

## 3. DHT20 手册中需要保留的硬件信息

### 3.1 供电和上电顺序

- 供电范围为 `2.2 V ~ 5.5 V`，本项目应采用与 STM32 一致的 `3.3 V`。
- 手册要求传感器 VDD 上电后等待至少 `5 ms`，之后才可以将 SCL、SDA 设置为高电平。
- 主机 MCU 与传感器的逻辑电压应保持一致。I2C 上拉不能接到高于 MCU GPIO 可承受范围的电源。
- 若以后增加传感器电源控制，应先打开 VDD，再等待 5 ms，最后释放 SCL/SDA。
- 当前 PB6/PB7 的板级配置为开漏、无内部上下拉、初始高电平。这里的“高电平”实际表示释放总线，真正的高电平由外部上拉产生。

当前实现需要特别确认：传感器模块是否在 MCU 初始化 GPIO 之前已经稳定供电。如果传感器和 MCU 同时上电，至少要在第一次 DHT20 事务前满足 5 ms 上电等待要求。

### 3.2 I2C 电气规则

DHT20 的 SDA 和 SCL 都是开漏/线与形式。MCU 只能主动拉低，不能通过推挽方式主动输出高电平：

```text
输出 LOW  -> MCU 拉低线路
输出 HIGH -> MCU 释放线路，由外部上拉拉高
读取      -> 读取 GPIO 实际线路电平
```

因此软件 I2C 不应使用推挽输出模拟高电平，也不应只读取 MCU 输出寄存器判断线路状态。SDA 在输出 HIGH 后应读取 GPIO 输入数据寄存器对应的实际电平，以便识别从机 ACK、总线被拉低和线路异常。

手册举例使用 `4.7 kΩ` 外部上拉。实际阻值应结合总线电容、连线长度、模块板上已有电阻和上拉电压确认，不能在已有模块带上拉的情况下再盲目并联过多电阻。

### 3.3 信号完整性

手册指出 SCL 和 SDA 长距离平行、过近布线可能造成串扰和通信失败；降低 SCL 频率可以提高稳定性。当前第一版软件 I2C 不追求 400 kHz，建议从约 `50~100 kHz` 开始，并用逻辑分析仪确认实际波形。

## 4. 软件 I2C 时序要求

### 4.1 手册时序的核心规则

- I2C 数据在 SCL 为高电平期间必须保持稳定。
- SDA 只允许在 SCL 为低电平期间改变；START 和 STOP 是例外。
- START：SCL 为高时，SDA 从高变低。
- STOP：SCL 为高时，SDA 从低变高。
- 发送数据时，SDA 在 SCL 上升沿前必须准备好。
- 读取数据时，从机在 SCL 变低后更新 SDA，主机应在 SCL 为高且信号稳定后采样。
- 每个字节传输 8 个数据位，随后是第 9 个 ACK/NACK 时钟。
- 数据按 MSB first 传输。

### 4.2 手册给出的时序边界

手册表 7 给出标准模式和快速模式参数。对当前软件 I2C，建议只按标准模式设计：

| 参数 | 标准模式要求 | 第一版建议 |
| --- | ---: | --- |
| SCL 频率 | 最大 100 kHz | 先使用约 50~100 kHz |
| SCL 低电平时间 | 不小于 4.7 μs | 保留余量，建议不小于 5 μs |
| SCL 高电平时间 | 不小于 4.0 μs | 保留余量，建议不小于 5 μs |
| SDA 建立时间 | 不小于 250 ns | 通过 GPIO 操作开销和短延时留出余量 |
| SDA 保持时间 | 满足手册最小值 | 不在 SDA 切换后立即抬高 SCL |

不要使用 `osDelay()` 或 FreeRTOS tick 延时实现单个位时序。软件 I2C 应注入独立的微秒级延时能力，例如 `delay_us()`；该接口的具体命名和归属需要在 Software I2C 专项设计中冻结。

### 4.3 基础位操作顺序

建议按以下顺序实现并逐步验证：

```text
写 0：SDA 拉低 -> 建立延时 -> SCL 释放为高 -> 保持 -> SCL 拉低
写 1：SDA 释放为高 -> 建立延时 -> SCL 释放为高 -> 保持 -> SCL 拉低

读 1 bit：SDA 释放 -> SCL 释放为高 -> 短暂等待 -> 读取 SDA -> SCL 拉低

写字节：MSB first 写 8 bit -> 释放 SDA -> 拉高 SCL -> 读取 ACK -> 拉低 SCL
读字节：逐 bit 释放 SDA/拉高 SCL/采样 -> 拉低 SCL -> 主机发送 ACK 或 NACK
```

ACK 的有效含义是 SDA 在第 9 个时钟期间为低；NACK 是 SDA 为高。发送 DHT20 命令时必须检查地址和每一个命令字节的 ACK，不能只检查最后一个字节。

## 5. DHT20 测量协议

### 5.1 测量命令

手册规定的单次测量事务为：

```text
START
发送写地址 0x70
等待 ACK
发送命令 0xAC
等待 ACK
发送参数 0x33
等待 ACK
发送参数 0x00
等待 ACK
STOP
```

发送完 `0xAC 0x33 0x00` 后，等待至少 `80 ms`，让传感器完成测量。

这里有两个容易出错的点：

1. `0x70` 和 `0x71` 是包含读写位的 8 位地址表示，不应在使用 7 位地址 API 时再次错误左移。
2. 测量命令结束后应先 STOP，再等待 80 ms；读取不是紧跟在命令后面的同一段连续写事务。

### 5.2 读取事务

80 ms 测量时间结束后，执行：

```text
START
发送读地址 0x71
等待 ACK
读取 data[0]，主机 ACK
读取 data[1]，主机 ACK
读取 data[2]，主机 ACK
读取 data[3]，主机 ACK
读取 data[4]，主机 ACK
读取 data[5]，主机 ACK
读取 data[6]，主机 NACK
STOP
```

总共读取 7 个字节：1 个状态字节、5 个有效载荷字节和 1 个 CRC 字节。

数据布局如下：

| 字节 | 内容 |
| --- | --- |
| `data[0]` | Status |
| `data[1]` | `S_RH[19:12]` |
| `data[2]` | `S_RH[11:4]` |
| `data[3]` | 高 4 位为 `S_RH[3:0]`，低 4 位为 `S_T[19:16]` |
| `data[4]` | `S_T[15:8]` |
| `data[5]` | `S_T[7:0]` |
| `data[6]` | CRC8 |

解析关系为：

```c
raw_rh = ((uint32_t)data[1] << 12)
       | ((uint32_t)data[2] << 4)
       | ((uint32_t)data[3] >> 4);

raw_t = (((uint32_t)data[3] & 0x0FU) << 16)
       | ((uint32_t)data[4] << 8)
       | (uint32_t)data[5];
```

最后一个 CRC 字节读取完成后，主机必须发送 NACK，表示本次读取结束，然后发送 STOP。最后一个字节错误地发送 ACK，可能导致总线结束行为不符合预期。

## 6. 状态字、CRC 和物理量换算

### 6.1 状态字

当前项目最需要关注的状态位：

| 位 | 含义 | 处理建议 |
| --- | --- | --- |
| Bit7 | Busy：1 表示测量中，0 表示空闲 | 80 ms 后仍为 1，应记录超时/忙状态并判本次读取失败 |
| Bit6:5 | 工作模式 | 当前单次命令按 CMD 模式理解，不把模式位当温湿度数据 |
| Bit4 | OTP 数据 CRC_flag | 为 0 时记录传感器内部校准数据完整性异常 |
| Bit3 | 校准计算使能 | 正常输出应为校准后的数据；异常时记录状态，不静默使用 |
| Bit2:0 | 保留或比较器状态 | 第一阶段不参与温湿度换算，保留原始状态便于诊断 |

`Status.Bit7` 是设备测量状态，不等同于最后数据帧的 CRC。两者需要分别处理。

### 6.2 CRC8

手册规定：

- CRC 初始值：`0xFF`
- 多项式：`0x31`，即 `x^8 + x^5 + x^4 + 1`
- 计算输入：`Status` 加上 5 个温湿度有效载荷字节，共 6 字节
- 计算结果与 `data[6]` 比较

等价的计算伪代码：

```c
crc = 0xFF;
for each byte in data[0] ... data[5]:
    crc ^= byte;
    repeat 8 times:
        if (crc & 0x80U):
            crc = (crc << 1) ^ 0x31U;
        else:
            crc = crc << 1;

return (uint8_t)crc;
```

CRC 错误时不得把数据继续交给 APP 发送为正常测量值。应返回明确的数据校验错误，由上层决定 RTT 日志、UART 错误响应和本次采集是否失败。

### 6.3 温度和湿度换算

有效数据是 20 位无符号原始值：

```c
relative_humidity = ((float)raw_rh / 1048576.0f) * 100.0f;
temperature_c     = ((float)raw_t / 1048576.0f) * 200.0f - 50.0f;
```

其中 `1048576 = 2^20`。建议同时保留原始 20 位值和换算后的浮点/定点结果，便于调试 CRC、边界和数据格式；第一阶段对外业务报告可直接使用温度和相对湿度物理量。

## 7. 推荐的软件 I2C / DHT20 调用流程

### 7.1 初始化阶段

```text
系统启动
  -> 确认 DHT20 供电和 3.3 V 上拉
  -> 构造 PB6 SCL / PB7 SDA GPIO 对象
  -> 配置为开漏输出、无内部上拉、初始释放
  -> 满足 VDD 上电后至少 5 ms
  -> 初始化 Software I2C 上下文
  -> 做一次总线空闲检查
  -> 通过一次真实 DHT20 测量验证通信、状态和 CRC
```

手册给出的相关章节没有要求在每次启动时额外发送一条复杂初始化命令。当前项目的“DHT20 初始化”应重点完成总线和设备可用性检查；是否增加独立状态查询，需要结合最终驱动接口专项设计确认，不要凭经验引入未验证命令。

### 7.2 单次读取流程

```text
dht20_read()
  -> Software I2C 写事务：0x70 + 0xAC + 0x33 + 0x00
  -> STOP
  -> 等待 80 ms（任务上下文）
  -> Software I2C 读事务：0x71 + 7 字节
  -> 检查总线事务结果
  -> 检查 Status.Bit7
  -> 计算并比较 CRC8
  -> 解析 20 位湿度/温度原始值
  -> 换算物理量
  -> 返回明确成功或错误码
```

80 ms 等待可以阻塞 Sensor Task，但不能放在 ISR、HAL Callback 或软件 I2C 中断上下文中。若将来有多个任务访问同一条总线，建议只在实际 I2C 写事务和读事务期间持有总线互斥量，不要无故持有互斥量等待 DHT20 内部测量完成。

## 8. 与现有工程架构的映射

### 8.1 Platform GPIO 的使用方式

当前 GPIO 抽象已经提供：

- `platform_gpio_write()`：拉低或释放开漏线；
- `platform_gpio_read()`：读取实际 GPIO 电平；
- `platform_gpio_configure()`：配置开漏输出和上下拉属性。

Software I2C 不应直接调用 `HAL_GPIO_WritePin()`、`HAL_GPIO_ReadPin()` 或操作 `GPIO_TypeDef`。PB6/PB7 的具体物理绑定由 BSP/Impl 保持，协议层只看到两个 GPIO 对象和微秒延时能力。

### 8.2 与 DHT20、MPU6050 的共用总线

第一阶段按项目需求使用一个采集执行上下文串行访问：

```text
一次采集周期
  -> DHT20 完整读数
  -> MPU6050 完整读数
  -> 组织业务报告
  -> 复用 UART DMA TX 发送
```

这样可以避免为了两个设备提前创建两个任务和一个复杂的总线仲裁框架。若未来确实出现多个并发访问者，互斥范围至少应覆盖一个完整的 START 到 STOP 事务，且不能只锁某一个字节。

### 8.3 与 APP、UART 和日志的边界

- APP 决定 `STOPPED/RUNNING`、5 s 周期和 `ONCE` 行为。
- DHT20 驱动只返回测量数据或明确错误。
- UART Service 继续负责 UART 数据流和 DMA 发送，不理解 DHT20 命令。
- 正常运行时不逐 bit、逐 byte 输出 I2C 日志。
- I2C NACK、总线超时、DHT20 Busy 超时、CRC 错误应在任务上下文转化为 WARN/ERROR RTT 日志。
- 单次采集只有在 DHT20、MPU6050 和业务发送均成功后，APP 才执行 LED 三闪。

## 9. 错误处理建议

建议至少区分以下错误，不要全部归为“传感器读取失败”：

| 错误 | 可能原因 | 处理 |
| --- | --- | --- |
| Bus not idle | SDA/SCL 被拉低、接线或上拉异常 | 停止事务，记录线路状态 |
| Address NACK | 地址错误、未供电、线路异常 | 返回设备未响应 |
| Command NACK | 命令帧或时序错误 | 检查软件 I2C 写字节和 ACK |
| Read NACK/short read | 读取阶段时序或 ACK/NACK 处理错误 | 丢弃本次帧 |
| Busy timeout | 80 ms 后仍在测量或设备异常 | 不使用本次数据 |
| Frame CRC mismatch | 数据被干扰或解析错误 | 丢弃本次数据，记录 CRC 错误 |
| OTP CRC_flag invalid | 传感器内部校准数据完整性异常 | 记录设备异常，必要时禁止数据上报 |
| Range invalid | 换算结果越界或原始数据异常 | 返回数据有效性错误，不静默钳位 |

事务失败后，软件 I2C 可以尝试释放 SDA/SCL 并检查总线恢复状态；是否执行额外的总线恢复脉冲，需要作为单独设计决定，不能在本次 DHT20 驱动中无边界增加复杂恢复逻辑。

## 10. 验证计划

### 10.1 逻辑分析仪验证

至少验证以下波形：

1. 空闲时 SCL、SDA 均为高。
2. START/STOP 条件符合定义。
3. 写地址为 `0x70`，读地址为 `0x71`，没有错误的二次移位。
4. `0xAC 0x33 0x00` 每个字节后都有从机 ACK。
5. 命令 STOP 到读 START 之间存在至少 80 ms 测量等待。
6. 读取长度为 7 字节，前 6 字节后主机 ACK，最后 CRC 后主机 NACK。
7. SCL 低/高电平时间达到标准模式下限。
8. SDA 在 SCL 高电平期间保持稳定，未出现推挽输出高电平。

### 10.2 软件测试

在 Host 环境优先测试不依赖真实 GPIO 的部分：

- 7 字节数据帧拆包；
- 20 位湿度和温度拼接；
- CRC8 正确帧和错误帧；
- 温度、湿度换算；
- Status.Bit7 忙状态处理；
- 各类错误码映射。

在真实开发板上测试：

- 无传感器/断开 SDA 或 SCL 时的 NACK 与超时；
- 正常单次采集；
- RUNNING 每 5 s 采集；
- 与 MPU6050 共用总线后的事务顺序；
- 传感器数据通过既有 UART DMA 链路输出；
- RTT 日志不进入业务 UART。

## 11. 当前不应提前加入的内容

以下内容不是 DHT20 接入第一阶段的必要条件：

- STM32 硬件 I2C 外设；
- 400 kHz 快速模式优化；
- DHT20 连续测量模式；
- 在 ISR 中执行 DHT20 测量；
- 为 DHT20 单独创建任务；
- 复杂的 I2C 总线恢复框架；
- 为一次 80 ms 测量等待建立复杂异步状态机；
- 将 I2C bit/ACK 日志长期打开；
- 修改 UART DMA + RingBuffer 现有数据链路；
- MPU6050 姿态融合、DMP、卡尔曼滤波。

## 12. 最终落地结论

DHT20 对当前项目最有价值的不是传感器性能参数，而是它提供了一个完整的“根据数据手册实现软件 I2C 设备驱动”的练习对象。实现顺序应固定为：

```text
先验证 GPIO 电气状态
  -> 再验证 START/STOP 和单字节 ACK
  -> 再验证 DHT20 写测量命令
  -> 再验证 80 ms 后读取 7 字节
  -> 再验证状态位和 CRC
  -> 最后接入温湿度换算、APP 周期采集和 UART 上报
```

当前工程已经具备 PB6/PB7 的 GPIO 抽象和板级绑定基础，但 Software I2C 的对象模型、微秒延时注入接口、DHT20 驱动公共 API 和测试合同仍应先经过专项设计再编码。这样可以保持现有 `APP -> Service -> Platform -> Impl` 依赖方向，也能把后续 MPU6050 接入复用到同一条软件 I2C 能力上。

当前阶段：阶段 10（驱动开发实战），正在从 GPIO 板级能力进入 Software I2C 和传感器驱动。

下一步建议：先冻结 Software I2C 的 GPIO 操作接口、微秒延时接口、错误码和最小事务 API，再用逻辑分析仪完成 DHT20 的写命令与 7 字节读取验证。
