# 第一部分：整体数据链路

## 1. 一分钟介绍传感器与显示链路

传感器：

```text
GPIO Soft I2C
   ↓
Platform I2C
   ↓
DHT20 / MPU6050 Platform Driver
   ↓
Acquisition Service
   ↓
Acquisition Task
   ↓
Display Queue
```

显示：

```text
Display Task
   ↓
APP Display
   ↓
Graphics / Text
   ↓
Platform ST7789
   ↓
Platform SPI + GPIO + Time
   ↓
STM32 Impl
   ↓
HAL / Hardware
```

核心设计点：

- shared I2C 的 runtime owner 是 Acquisition Task；
- ST7789/Graphics 的 runtime owner 是 Display Task；
- 传感器和 LCD 不直接互相依赖；
- Acquisition 成功不要求 LCD 一定显示成功；
- 显示属于 non-critical output subsystem。

# 第二部分：软件 I2C

## 2. 为什么当前使用软件 I2C？

软件 I2C 的价值：

- GPIO 绑定灵活；
- 更容易观察协议细节；
- 便于学习 START/STOP/ACK/Clock Stretching；
- 可以作为 Platform 总线能力实现。

代价：

- CPU 占用高于硬件 I2C；
- 时序精度受软件延时和中断影响；
- 高速能力有限；
- 复杂错误恢复需要自己实现。

因此当前方案适合低速传感器采集，不代表量产高吞吐场景一定优先 bit-bang。

---

# 3. I2C 为什么是开漏？

I2C SDA/SCL 通常使用 open-drain/open-collector + pull-up。

设备只能：

```text
主动拉低
或
释放线路
```

不能主动驱动高。

好处：

- 多设备可以共享总线；
- wired-AND；
- 支持 arbitration；
- 支持 Clock Stretching。

### “写 HIGH”到底是什么意思？

在 open-drain 语义里：

```text
write HIGH
≈ release line
```

真正高电平由上拉电阻产生。

---

# 4. START / STOP 条件

START：

```text
SCL = HIGH 时
SDA: HIGH → LOW
```

STOP：

```text
SCL = HIGH 时
SDA: LOW → HIGH
```

这也是为什么 I2C 不只是“GPIO 按固定顺序翻转”，而是特定 SDA/SCL 相对时序。

---

# 5. ACK / NACK

每传输 8 bit 后，第 9 个 clock 用于 ACK/NACK。

ACK：

```text
SDA = LOW
```

NACK：

```text
SDA = HIGH
```

写操作：

- master 发 8 bit；
- slave 在第 9 bit ACK。

读操作：

- slave 发 8 bit；
- master 在第 9 bit 决定 ACK/NACK。

读取最后一个 byte 后通常由 master 发 NACK，表示不再继续读取。

---

# 6. 7-bit 地址如何上总线？

协议 byte：

```text
[address 7 bit][R/W 1 bit]
```

代码逻辑：

```text
addressByte = address << 1
if read:
    addressByte |= 1
```

因此 DHT20 的 0x38、MPU6050 的 0x68 是 7-bit 地址，不应该在上层重复左移后再传。

---

# 7. Repeated START 有什么用？

典型寄存器读取：

```text
START
ADDR + W
REGISTER
REPEATED START
ADDR + R
DATA...
STOP
```

它允许在不释放总线的情况下从“写寄存器地址”切换到“读寄存器数据”。

MPU6050 的 write_read 就属于这种典型模式。

---

# 8. Clock Stretching 是什么？

slave 可以主动拉低 SCL，延迟 master 的下一个 clock。

因此 master “释放 SCL”后不能假设物理 SCL 已经变 HIGH。

当前软件 I2C：

```text
release SCL
→ read physical SCL
→ loop until HIGH or timeout
```

当前：

```text
SCL timeout = 100 us
```

### 为什么需要 timeout？

如果从机故障或线路被永久拉低，没有 timeout：

```text
while(SCL == LOW)
```

可能永久死锁。

---

# 9. I2C 总线为什么会卡死？

常见场景：

- MCU 在一个 transaction 中途 reset；
- slave 仍认为 transaction 未完成；
- SDA 被 slave 拉低；
- master 重启后发现 bus busy。

典型 bus recovery：

```text
释放 SDA
→ 产生最多 9 个 SCL pulse
→ 尝试让 slave 释放 SDA
→ STOP
```

为什么常见是 9 个 clock？

因为从机最多可能正处于一个 byte 的 8 bit + ACK 阶段，额外 clock 可以推动其内部状态机完成当前 byte。

# 第三部分：DHT20

## 10. DHT20 当前读取流程

当前地址：

```text
0x38
```

触发测量：

```text
AC 33 00
```

等待：

```text
80 ms
```

读取：

```text
7 Byte frame
```

检查：

- BUSY；
- CRC flag；
- calibration enable；
- CRC8。

只有完整检查通过才提交 measurement。

---

# 11. DHT20 CRC

当前：

```text
CRC-8
initial = 0xFF
polynomial = 0x31
data length = 前 6 bytes
第 7 byte = CRC
```

### 为什么传感器还要 CRC？

I2C 本身 ACK 只说明每个 byte 层面被接收，不保证整个 payload 没有由于干扰、时序异常等发生错误。

传感器协议 CRC 提供 payload 完整性检查。

---

# 12. DHT20 20-bit 数据怎么解析？

湿度 raw：

```text
frame[1]
frame[2]
frame[3] high nibble
```

温度 raw：

```text
frame[3] low nibble
frame[4]
frame[5]
```

都是 20 bit。

换算：

```text
humidity = rawHumidity * 100 / 2^20

temperature = rawTemperature * 200 / 2^20 - 50
```

当前代码使用：

```text
1048576 = 2^20
```

---

# 13. 为什么先解析到 localMeasurement，再赋给输出？

代码先：

```text
localMeasurement
```

完成所有检查和解析后：

```text
*measurement = localMeasurement
```

避免中间失败时把调用方输出对象更新成半有效状态。

这是很小但很重要的 transaction/commit 思想。

# 第四部分：MPU6050

## 14. MPU6050 初始化为什么先读 WHO_AM_I？

寄存器：

```text
WHO_AM_I = 0x75
```

当前期望：

```text
0x68
```

目的：

- 确认总线上确实存在目标设备；
- 避免对错误地址/错误器件继续写配置；
- bring-up 时快速定位 wiring/address 问题。

---

# 15. MPU6050 当前初始化配置

依次写：

```text
PWR_MGMT_1
CONFIG
SMPLRT_DIV
GYRO_CONFIG
ACCEL_CONFIG
```

当前：

```text
GYRO_CONFIG  = 0
ACCEL_CONFIG = 0
```

对应：

```text
Gyro  ±250 dps
Accel ±2 g
```

比例：

```text
Accel = 16384 LSB/g
Gyro  = 131 LSB/(°/s)
```

---

# 16. 为什么连续读取 14 Byte？

从：

```text
ACCEL_XOUT_H = 0x3B
```

开始连续寄存器包括：

```text
Accel X
Accel Y
Accel Z
Temperature
Gyro X
Gyro Y
Gyro Z
```

一次连续读取：

- transaction 数更少；
- 数据时间一致性更好；
- 比每个轴单独发 I2C transaction 更高效。

当前业务不需要 MPU 内部温度，所以解析时跳过对应两个 byte。

---

# 17. 为什么 axis 要拼成 int16_t？

MPU6050 输出为高字节在前的 16-bit two's complement。

组合：

```text
(high << 8) | low
```

然后 cast 为：

```text
int16_t
```

这样负值可以按补码正确解释。

之后：

```text
accelG = raw / 16384
gyroDps = raw / 131
```

# 第五部分：Acquisition Service

## 18. 为什么还需要 Acquisition Service？

DHT20 和 MPU6050 Driver 只知道自己的设备。

业务希望得到：

```text
environment + motion
```

一份统一 snapshot。

Acquisition Service 定义：

```text
DHT20 success
AND
MPU6050 success
= acquisition success
```

它把两个设备能力组合成稳定 Service contract。

---

# 19. 为什么要原子提交双传感器结果？

当前：

```text
temporaryData
├─ environment
└─ motion
```

先读两者。

只有：

```text
DHT20 == OK
&&
MPU6050 == OK
```

才：

```text
*data = temporaryData
```

否则整个 sample 失败。

避免：

```text
environment = 本轮新值
motion      = 上一轮旧值
```

这种混合 snapshot。

### 这是不是唯一正确设计？

不是。

如果业务允许“部分数据有效”，可以给每个 sensor 独立 valid flag。

当前项目选择 atomic snapshot，是为了让上层语义更简单。

---

# 20. 为什么两个传感器共用 I2C 没有 Mutex？

因为 runtime owner 是 Acquisition Task。

只有该 Task 调用 DHT20/MPU6050。

所以：

```text
shared bus
≠ shared concurrent access
```

即使物理上两设备共享总线，也没有多个 Task 同时访问，因此不需要 mutex。

这是 ownership 设计的重要例子。

# 第六部分：SPI 基础

## 21. SPI 和 I2C 核心区别

SPI 通常：

```text
SCLK
MOSI
MISO
CS
```

特点：

- 全双工移位；
- 没有像 I2C 一样的总线地址阶段；
- slave 通常通过 CS 选择；
- 不自带 ACK；
- 时钟由 master 提供；
- 一般速度高于软件 I2C。

当前 ST7789 场景主要：

```text
MOSI + SCLK + CS
```

显示驱动基本只向 LCD 写。

---

# 22. CPOL / CPHA 是什么？

CPOL：

> 空闲时钟电平。

CPHA：

> 在第一个还是第二个有效边沿采样。

组合形成常见 SPI Mode 0~3。

面试时不一定要死背每个 Mode 数字对应值，但必须理解：

> 主从双方 CPOL/CPHA 必须匹配，否则采样边沿错位，数据会错误。

---

# 23. ST7789 的 CS / DC / RST / BL 分别做什么？

CS：

```text
Chip Select
```

选择 LCD slave。

DC：

```text
Data / Command select
```

告诉 LCD 当前 SPI byte 是命令还是参数/像素数据。

RST：

```text
hardware reset
```

BL：

```text
backlight control
```

### 为什么 SPI 没有 I2C 地址？

SPI 通常通过独立 CS 线选择 slave，所以协议里不需要 7-bit address byte。

# 第七部分：ST7789 与显示资源

## 24. 为什么不用 full framebuffer？

屏幕：

```text
240 × 280
RGB565
2 Byte / pixel
```

full framebuffer：

```text
240 * 280 * 2
= 134400 B
≈ 131.25 KiB
```

对于当前 STM32F411 SRAM 资源不合适。

因此当前采用：

```text
small fixed scratch buffer
+
chunked SPI write
```

而不是整屏 framebuffer。

---

# 25. RGB565 是什么？

16-bit pixel：

```text
R: 5 bit
G: 6 bit
B: 5 bit
```

共：

```text
2 Byte / pixel
```

绿色多 1 bit 是因为人眼对绿色更敏感，可以获得更好的主观色彩分辨率。

---

# 26. 为什么使用局部刷新？

UI 中很多内容是静态的：

- title；
- label；
- section name。

动态区域只有：

- RUNNING/STOPPED；
- 温湿度；
- accel；
- gyro。

如果每次全屏刷新：

```text
240 * 280 * 2
```

产生大量无效 SPI traffic。

当前只：

```text
clear dynamic rect
→ redraw changed value
```

降低显示带宽和 Display Task 阻塞时间。

---

# 27. 为什么 Display 单独一个 Task？

SPI 当前是 blocking synchronous TX。

如果 Acquisition 采完直接刷屏：

```text
Acquisition
→ blocking LCD SPI
→ 下一轮业务被显示时间影响
```

独立 Display Task：

```text
Acquisition / Control
→ Display Queue
→ Display owner
→ LCD
```

把显示延迟隔离在显示子系统。

---

# 28. 为什么 Display failure 不影响 Acquisition success？

当前定义：

```text
Acquisition success
= 两个传感器数据成功获得
```

而不是：

```text
采集成功
AND
LCD 成功画出来
```

否则屏幕坏了会导致核心采集业务被判失败。

因此：

```text
Acquisition Success
Display Success
Communication Success
```

是不同 failure domain。

---

# 29. Display Queue 为什么允许 best effort？

LCD 是 presentation。

如果 Display Queue 满：

```text
Producer 不应该因为 LCD 慢而阻塞核心控制/采集
```

因此发送可 NO_WAIT。

Display consumer 还会：

```text
wait first
→ drain backlog
→ update cache
→ render latest once
```

减少重复刷新。

---

# 30. 为什么当前 SPI 不用 DMA？

当前阶段目标是：

- 验证显示链路；
- 验证 ownership；
- 验证 Platform SPI；
- 显示刷新频率不高。

blocking SPI 实现更简单。

代价：

- Display Task 发送期间 CPU 参与等待；
- 大块刷新效率有限；
- 不适合高帧率 GUI。

后续 F407 + LVGL 项目更适合演进：

```text
LVGL draw buffer
→ flush callback
→ SPI DMA
→ completion
→ lv_display_flush_ready
```

甚至结合：

- double buffer；
- partial buffer；
- DMA；
- dirty area。

---

# 31. SPI 时钟是不是越高越好？

不是。

限制来自：

- MCU SPI clock；
- LCD controller specification；
- PCB/杜邦线 signal integrity；
- 电平转换；
- rise/fall time；
- wiring length；
- 实际模块质量。

当前项目配置上限：

```text
12.5 MHz
```

如果继续提高出现：

- 花屏；
- 随机像素；
- 初始化失败；

应首先检查 SPI waveform 和时序，而不是默认软件逻辑错误。

---

# 32. 当前显示方案与 LVGL 有什么关系？

当前显示是自建 minimal graphics/text pipeline。

它帮助理解：

- pixel format；
- draw region；
- SPI transaction；
- display ownership；
- partial refresh；
- framebuffer 资源。

迁移 LVGL 后，这些基础仍存在，只是上层对象/布局/事件交给 LVGL。

典型结构：

```text
LVGL
→ draw buffer
→ flush callback
→ Platform Display/SPI
→ Hardware
```

# 33. 常见故障排查

## I2C 全部读不到

检查：

- SDA/SCL 引脚；
- open-drain；
- pull-up；
- 7-bit address；
- START；
- ACK；
- 逻辑分析仪。

## 某个传感器 NACK

检查：

- address；
- 电源；
- 初始化状态；
- wiring；
- device busy；
- bus recovery。

## DHT20 CRC 错

检查：

- frame 是否 7 byte；
- CRC polynomial/initial；
- I2C waveform；
- 测量等待时间；
- 线路干扰。

## MPU6050 WHO_AM_I 不对

检查：

- AD0 导致 0x68/0x69；
- register 0x75；
- repeated START；
- byte order。

## LCD 白屏/黑屏

检查：

- power/backlight；
- RST；
- CS；
- DC；
- init sequence；
- SPI mode；
- coordinate offset。

## LCD 花屏

检查：

- SPI clock 过高；
- pixel data length；
- address window；
- RGB565 byte order；
- signal integrity。

# 34. 当前方案的边界

1. 软件 I2C CPU 占用高，不适合高吞吐；
2. 传感器 transaction 当前同步阻塞；
3. dual-sensor sample 采用“全有或全无”，不支持 partial-valid；
4. MPU6050 当前没有复杂校准/滤波/姿态融合；
5. ST7789 当前无 full framebuffer；
6. SPI 当前无 DMA；
7. UI 是 minimal graphics，不是 LVGL；
8. Display Queue best effort，极端情况下 presentation 可短暂滞后；
9. 当前资源参数主要是 bring-up baseline，不代表极限性能。
