# 五层架构设计面试手稿

> 目标：面试时不只会说“分层降低耦合”，而是能从需求、变化点、资源所有权、生命周期和迁移成本重新推导当前设计。

---

## 1. 一分钟介绍整体架构

### Q：你这个项目的软件架构是什么？

推荐回答：

本工程按五层组织：

```text
APP
 ↓
Service
 ↓
Platform
 ↓
Impl
 ↓
Vendor / HAL / RTOS / Hardware
```

其中：

- APP 负责产品业务，包括 Communication、Control、Acquisition、Display、Indicator 五个产品任务，以及 Control FSM、周期采集和页面编排；
- Service 负责不绑定具体 MCU 的可复用能力，例如 UART Service、Button Service、Acquisition Service；
- Platform 定义 UART、GPIO、I2C、SPI、RTOS Queue/Thread/Notify 等能力接口；
- Impl 把 Platform 接口具体适配到 STM32 HAL 和 CMSIS-RTOS2/FreeRTOS；
- Vendor 是 HAL、CMSIS、FreeRTOS 等第三方或芯片相关代码。

当前依赖约束：

```text
允许：
APP -> Service
APP -> Platform
Service -> Platform
Platform -> Impl

禁止：
APP -> Impl
Service -> Impl
```

核心目标不是单纯“层数更多”，而是把产品业务、可复用能力、硬件能力接口和具体芯片实现隔离，使变化尽量局部化。

---

## 2. 为什么要做五层？是不是过度设计？

### Q：一个 STM32 项目做五层是不是太重？

推荐回答：

如果只是点灯、读传感器或者一次性 Demo，五层确实偏重。这个工程除了完成产品功能，还有验证长期复用资产的目的，例如 UART DMA、RTOS Adapter、GPIO/I2C/SPI Platform 接口希望在后续 F407 项目继续使用，所以我有意隔离业务和硬件实现。

收益：

- F411 → F407 时，上层 APP/Service 尽量不变；
- HAL/FreeRTOS API 不直接泄漏到业务层；
- 驱动和 Service 可以独立做 host test；
- ownership、错误语义和生命周期更容易明确。

代价：

- 文件数量多；
- 调用链更长；
- 类型和生命周期管理更复杂；
- 对很小的项目开发成本偏高。

因此这是面向复用和演进的工程取舍，不是所有 MCU 项目的通用最佳方案。

### 深挖：Bootloader 为什么不照搬？

Bootloader 功能集中、空间敏感、启动链路要求简单，因此应该主动减少层次。分层是控制复杂度的手段，不是目标。

## 3. APP 和 Service 怎么区分？

### Q：APP 和 Service 看起来都在写业务，有什么明确边界？

核心判断：

> 是否包含当前产品特有的业务状态和业务流程。

APP 负责：

```text
START / STOP / ONCE
Control FSM
任务调度
事件来源
产品成功语义
页面编排
```

Service 负责相对稳定、可复用的能力：

```text
UART session
Button gesture
Dual-sensor acquisition
Indicator semantic execution
```

### 例子：Acquisition

`service_acquisition_sample()` 只负责：

```text
DHT20 read
MPU6050 read
两者都成功才提交完整结果
```

它不知道：

- 当前系统 RUNNING 还是 STOPPED；
- 本次是周期采样还是 ONCE；
- 数据最终显示还是通信；
- STOP 是否刚到。

这些由 APP Acquisition / Control 决定。

### 例子：UART

UART Service 管理：

- RX Session；
- RingBuffer；
- TX transaction；
- error/statistics；
- owner thread 唤醒。

它不知道 `START\r\n` 或 `STOP\r\n` 的业务含义。命令解释属于 Communication APP。

### 易错回答

不要只说“Service 是驱动上一层”。更准确的是：

> Service 把一个或多个 Platform 能力组织成与具体 MCU 无关、且有稳定行为合同的可复用能力。

---

## 4. Platform 和 Impl 怎么区分？

### Q：为什么还要把 Platform 和 Impl 分开？

用 UART 举例。

Platform UART 定义系统需要什么：

```text
read
write
read_async
write_async
cancel
callback
lifecycle
```

而 Impl 决定 STM32 上怎么做到：

```text
HAL_UART_Transmit_DMA
HAL_UARTEx_ReceiveToIdle_DMA
UART_HandleTypeDef
USART1
DMA
HAL callback
```

所以：

```text
Platform = what capability is required
Impl     = how this target implements it
```

如果以后换 MCU，Platform contract 可以尽量保持，上层不用知道底层从 USART1 换成 USART3 或 DMA mapping 发生变化。

---

## 5. BSP 的作用是什么？

### Q：Platform、BSP、Impl 三个概念怎么区分？

BSP 解决的是“这块板上的哪一个物理资源承担哪个逻辑角色”。

例如：

```text
逻辑角色：communication UART
                ↓
BSP binding：板上的某个 UART
                ↓
Impl：STM32 HAL 的具体 UART/DMA 实现
```

因此：

- Platform：定义能力；
- BSP：定义板级绑定；
- Impl：实现目标 MCU 的具体能力。

BSP 的价值在于不让 APP 知道“通信口刚好是 USART1、某个引脚和某个 DMA Stream”。

---

## 6. 为什么 APP 可以直接访问 Platform？

### Q：严格分层不是应该 APP → Service → Platform 吗？

当前工程不是机械的“只能访问下一层”，而是受控依赖方向。

只有当某个能力需要组合成稳定 Service 语义时，才引入 Service。

例如 Display：

```text
APP Display
   ↓
Platform ST7789 / Graphics
```

没有必要为了层数完整再造一个空壳 Display Service。

而双传感器采集存在组合语义和统一成功条件，所以：

```text
APP Acquisition
   ↓
Acquisition Service
   ↓
DHT20 / MPU6050 Platform Driver
```

更合理。

---

## 7. app_system.c 为什么像一个“大文件”？

### Q：为什么很多对象都集中在 app_system.c？

它承担 Composition Root。

职责：

```text
对象创建
依赖绑定
静态存储绑定
Queue 创建
Task 创建
Service 组合
初始化失败 rollback
```

模块内部只关心自己的行为和传入依赖，不自己到处寻找全局对象。

### Q：这算依赖注入吗？

可以说是依赖注入思想，但不是复杂 DI Framework。

当前方式是：

```text
manual composition root
+
config struct
+
explicit pointer binding
```

对于 C 嵌入式更轻量，也更容易看清 ownership。

## 8. Ownership 为什么是架构核心？

当前运行期 owner：

```text
Communication Task = USART1 communication owner
Control Task       = STOPPED/RUNNING FSM owner
Acquisition Task   = DHT20/MPU6050/shared-I2C owner
Display Task       = ST7789/Graphics owner
Indicator Task     = LED semantic owner
```

### Q：为什么不让多个 Task 都访问硬件，然后加 Mutex？

因为共享越多，需要解决的问题越多：

- transaction interleave；
- mutex；
- priority inversion；
- deinit 期间谁还能访问；
- error recovery 谁负责；
- ownership 转移。

当前优先使用：

> single owner + message passing

把很多并发问题从设计上消掉，而不是事后用锁修补。

### 高级表达

> 我优先通过 ownership 消除共享，再在确实需要共享时考虑互斥。

---

## 9. business truth has one owner 是什么意思？

Control Task 是唯一业务状态真值拥有者：

```text
STOPPED
RUNNING
```

其他模块中的状态并不具有相同语义：

- Display 的 RUNNING/STOPPED 是 presentation snapshot；
- Acquisition 的 periodicEnabled 是执行器内部状态；
- Communication 只负责输入和响应。

如果多个模块各自维护一个“真正 RUNNING”，容易出现：

```text
Control = RUNNING
Acquisition = STOPPED
Display = RUNNING
```

即状态分裂。

---

## 10. START 为什么先向 Acquisition 投递命令，再改 Control 状态？

正确顺序：

```text
Control
 ↓
send START_PERIODIC
 ↓ accepted
state = RUNNING
```

如果反过来：

```text
state = RUNNING
↓
Acquisition Queue full / send fail
↓
采集实际未启动
```

业务真值和执行器会不一致。

这可以理解为一个很轻量的“先保证关键下游操作接受，再提交状态”。

### Q：那 Display/LED/UART response 失败为什么不 rollback RUNNING？

因为它们不是 START 的核心成功条件，而是输出/反馈子系统。

当前系统明确区分：

```text
Acquisition success
Display success
Communication success
Indicator success
```

一个非关键输出失败不能把核心业务成功语义污染掉。

---

## 11. ONCE 为什么不是第三个主 FSM 状态？

当前：

```text
durable mode:
STOPPED
RUNNING

orthogonal operation context:
onceActive
onceSource
```

ONCE 是瞬态事务，不是长期系统模式。

如果所有瞬态操作都塞进主 FSM，未来会形成状态组合膨胀：

```text
STOPPED
RUNNING
STOPPED_ONCE
RUNNING_ONCE
...
```

当前产品还明确禁止 RUNNING 下执行 ONCE，因此用独立 operation context 更简单。

### 什么时候应该升级为正式状态？

如果以后：

- ONCE 可取消；
- 有多阶段采集；
- UI 要展示长时间 SAMPLING；
- 允许复杂并发转换；

那么独立 FSM 状态可能更合适。

---

## 12. 为什么要有完整 lifecycle？

Platform 对象区分：

```text
construct
init
start
stop
deinit
```

因为“对象存在”和“设备正在运行”不同。

以 UART 为例，需要区分：

- 对象已绑定但 HAL 未初始化；
- HAL 已初始化但未启动；
- 正在接受读写；
- DMA session 活跃；
- 已停止；
- 可以反初始化。

它可以防止：

```text
未 init 就 read
DMA active 时 deinit
stop 后继续发起 transaction
```

代价是状态机更复杂。不是所有简单驱动都需要这么完整。

---

## 13. 为什么初始化失败要逆序 rollback？

系统创建通常存在依赖：

```text
Platform device
→ Service
→ Queue
→ APP object
→ Task
```

如果中途失败，应逆序释放：

```text
Task
→ APP dependent resources
→ Queue
→ Service
→ Platform device
```

因为后创建对象往往依赖先创建对象。

若先销毁底层依赖，上层 deinit 可能访问已经失效的资源。

当前 `app_system_rollback()` 就是在做这种局部构造失败恢复。

---

## 14. Queue 为什么 copy-by-value？

项目原则：

```text
Queue copy-by-value
never enqueue stack pointer
```

危险例子：

```c
void foo(void)
{
    message_t msg;
    send_pointer(&msg);
}
```

如果 consumer 稍后才处理：

```text
foo return
→ stack frame reused
→ pointer dangling
```

copy-by-value 把消息内容复制进 Queue 自己的 storage，生命周期清楚。

### 代价

大结构体复制会有成本。

未来数据量大时可以改：

- memory pool；
- static buffer ownership transfer；
- descriptor queue；
- zero-copy scheme。

---

## 15. 为什么统一 platform_error_t？

HAL、CMSIS-RTOS2、驱动都有自己的错误码。

如果直接向上暴露：

```text
APP/Service
→ HAL_StatusTypeDef
→ osStatus_t
```

上层就被 Vendor API 污染。

统一成 `platform_error_t` 后，上层只处理一致语义：

```text
OK
TIMEOUT
BUSY
OVERFLOW
INVALID_STATE
...
```

### 边界

统一错误码可能损失底层细节，所以调试时仍应结合：

- 原始 HAL ErrorCode；
- RTT/elog；
- statistics；
- cmBacktrace 等诊断信息。

---

## 16. 为什么状态和 statistics 用 getter？

不直接暴露内部可写对象可以：

- 防止上层任意修改；
- 把内部布局与外部 contract 分开；
- 明确“这是 snapshot，不是真值所有权转移”。

UART statistics 还定义为 best-effort snapshot，不为了多字段完全同时一致而加锁/关中断。

这是因为统计是可观测性，不是核心事务状态。

---

## 17. no runtime malloc/free 应该怎么准确表达？

这是面试时必须谨慎的点。

当前业务层：

- APP/Service 对象为静态对象；
- DMA RX storage 为静态数组；
- RingBuffer storage 为静态数组；
- 业务运行阶段不自行 malloc/free。

但当前 CMSIS-RTOS2 Adapter 创建线程时：

```text
cb_mem = NULL
stack_mem = NULL
osThreadNew(...)
```

Queue 也：

```text
osMessageQueueNew(..., attr = NULL)
```

因此不能声称“整个 RTOS 完全静态分配”。

准确说法：

> 业务资源采用静态 ownership，应用运行阶段没有自行动态 malloc/free；但当前 RTOS 内核对象创建没有显式提供 static control block/stack storage，因此内核对象仍可能使用 FreeRTOS heap。

## 18. F411 → F407 时哪些层应该变化？

理想预期：

### 尽量不变

```text
APP
Service
Platform public contract
```

### 主要变化

```text
BSP binding
Impl
CubeMX
clock tree
pin mux
DMA mapping
peripheral instance
memory/resource config
```

### Platform 什么时候也应该改？

如果新平台能力本身不同，例如：

- 使用 FSMC/FMC 显示；
- 新增 CAN/Ethernet；
- 当前 UART/SPI 抽象暴露能力不够；

Platform contract 可以演进。

不要把“Platform 永远不变”说成教条。

---

## 19. 如果换 RTOS 呢？

如果从 FreeRTOS/CMSIS-RTOS2 换成 Zephyr：

- APP 业务逻辑理论上尽量保持；
- Service 尽量保持；
- Platform OS API 尽量保持；
- Impl OS Adapter 变化最大；
- startup、device model、thread semantics 可能迫使 Platform contract 调整。

这正是 OS abstraction 的目标，但不是保证“零修改”。

---

## 20. 当前架构有哪些明确不足？

面试时主动承认：

1. 对一个小型 STM32 项目来说抽象层偏多；
2. 部分 Platform API 目前只有一个 concrete implementation，复用价值仍需要在后续 F407 项目验证；
3. RTOS kernel object 目前不一定完全静态分配；
4. 传感器和 SPI Display 仍是同步阻塞式，简化了 ownership，但限制吞吐；
5. 接口和对象状态较多，需要较严格文档和测试才能避免“抽象本身成为复杂度来源”。
