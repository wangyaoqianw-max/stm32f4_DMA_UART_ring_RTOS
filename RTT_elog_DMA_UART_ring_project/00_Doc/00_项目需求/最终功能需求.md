# 最终功能需求

## 1. 文档目的

本文档用于收束 `stm32f4_DMA_UART_ring_RTOS` 项目的最终综合实现范围，作为后续 GPIO、软件 I2C、传感器、按键事件、APP 状态机及串口联调的统一功能基线。

本阶段不继续扩展 SPI/LCD、外部 Flash 等外围功能，优先完成一个可稳定运行、可通过本地按键和 PC 串口指令控制的数据采集闭环。

---

## 2. 最终硬件组成

- MCU：STM32F411
- 温湿度传感器：DHT20
- 六轴惯性传感器：MPU6050
- 用户按键：1 个
- 状态 LED：1 个
- PC：通过 UART 串口助手进行控制与数据显示

DHT20 与 MPU6050 共用一条软件 I2C 总线。

软件 I2C 基于 GPIO 模拟实现，不使用 STM32 硬件 I2C 外设。

---

## 3. 系统默认状态

系统启动并完成初始化后：

- 数据采集功能默认关闭；
- LED 默认熄灭；
- DHT20 不进行周期采集；
- MPU6050 不进行周期采集；
- UART 接收功能保持工作，可随时接收 PC 端控制指令；
- RTT / EasyLogger 日志功能保持正常工作。

系统逻辑状态至少包括：

- `STOPPED`：周期采集关闭；
- `RUNNING`：周期采集开启。

APP 层作为采集状态的唯一维护者，按键和 UART 命令只产生控制事件，不直接操作传感器状态。

---

## 4. 按键控制需求

### 4.1 短按一次

当系统处于 `STOPPED` 状态时：

- 单击按键；
- 系统进入 `RUNNING` 状态；
- LED 点亮；
- 启动 DHT20 周期采集；
- 启动 MPU6050 周期采集；
- 采集结果通过现有 UART 发送链路持续发送至 PC 串口助手。

当系统已经处于 `RUNNING` 状态时，单击不改变系统状态。

### 4.2 长按

当按键持续按下时间达到或超过 3 s，且系统处于 `RUNNING` 状态时：

- 停止周期采集；
- 系统进入 `STOPPED` 状态；
- LED 熄灭。

当系统已经处于 `STOPPED` 状态时，长按不执行额外操作。

### 4.3 双击

当系统处于 `STOPPED` 状态时：

- 在双击判定时间窗内连续短按两次；
- DHT20 采集一次；
- MPU6050 采集一次；
- 将本次采集结果通过 UART 发送至 PC；
- 采集完成后仍保持 `STOPPED` 状态；
- LED 保持熄灭。

当系统处于 `RUNNING` 状态时，双击不执行额外单次采集。

### 4.4 单击与双击判定

由于双击包含第一次短按，单击事件不得在第一次释放后立即执行。

按键服务应设置双击判定时间窗，在时间窗结束后再确认单击；若时间窗内出现第二次有效短按，则产生双击事件。

具体判定时间、消抖时间等参数应放入配置层统一管理，不在业务代码中散布魔法数字。

---

## 5. UART 控制需求

PC 串口助手可以通过 UART 向设备发送文本命令。

第一阶段定义以下基础命令：

```text
START\r\n
STOP\r\n
ONCE\r\n
STATUS\r\n
HELP\r\n
```

### 5.1 START

- `STOPPED` 状态：进入 `RUNNING`，LED 点亮并开始周期采集；
- `RUNNING` 状态：保持当前状态，并返回已处于运行状态的信息。

### 5.2 STOP

- `RUNNING` 状态：停止周期采集，进入 `STOPPED`，LED 熄灭；
- `STOPPED` 状态：保持当前状态，并返回已停止的信息。

### 5.3 ONCE

- `STOPPED` 状态：DHT20 与 MPU6050 各采集一次，将数据通过 UART 发送至 PC，完成后保持 `STOPPED`；
- `RUNNING` 状态：不执行额外采样，返回当前已经处于连续采集状态的信息。

### 5.4 STATUS

返回当前系统采集状态，例如：

```text
STATE=STOPPED\r\n
```

或：

```text
STATE=RUNNING\r\n
```

### 5.5 HELP

返回当前支持的基础控制命令列表。

## 6. 控制事件统一原则

按键和 UART 是两个不同的输入源，但不得分别维护两套业务状态。

推荐统一转换为 APP 控制事件：

```text
APP_CTRL_START
APP_CTRL_STOP
APP_CTRL_SAMPLE_ONCE
APP_CTRL_GET_STATUS
```

事件映射关系：

| 输入源 | 操作 | APP 控制事件 |
| --- | --- | --- |
| 按键 | 单击 | `APP_CTRL_START` |
| 按键 | 双击 | `APP_CTRL_SAMPLE_ONCE` |
| 按键 | 长按 >= 3 s | `APP_CTRL_STOP` |
| UART | `START` | `APP_CTRL_START` |
| UART | `STOP` | `APP_CTRL_STOP` |
| UART | `ONCE` | `APP_CTRL_SAMPLE_ONCE` |
| UART | `STATUS` | `APP_CTRL_GET_STATUS` |

最终由 APP 层状态机统一决定是否执行事件。

## 7. 传感器采集需求

### 7.1 DHT20

采集内容：

- 温度；
- 相对湿度。

DHT20 属于低速环境量传感器，不要求与 MPU6050 使用相同采样周期。

第一阶段建议使用约 1 Hz 的周期采样频率，最终参数由配置层定义。

### 7.2 MPU6050

第一阶段必须采集：

- Accel X；
- Accel Y；
- Accel Z；
- Gyro X；
- Gyro Y；
- Gyro Z。

可选扩展：

- Roll；
- Pitch。

第一阶段不要求实现长期稳定的绝对 Yaw 航向角。

MPU6050 采样频率独立于 DHT20，最终周期由配置层定义。

---

## 8. 软件 I2C 需求

软件 I2C 基于现有 GPIO Platform 能力实现。

基本能力至少包括：

- START；
- STOP；
- ACK / NACK；
- Byte Write；
- Byte Read；
- 连续数据读写；
- 寄存器读写能力。

软件 I2C 协议逻辑不得直接依赖 STM32 HAL GPIO API，应通过 Platform GPIO 抽象访问 SCL 与 SDA。

软件 I2C 所需微秒级延时应通过独立延时能力实现，不直接使用阻塞时间过大的 RTOS 延时接口模拟位时序。

DHT20 与 MPU6050 共用同一条软件 I2C 总线。

若第一阶段由单一 Sensor Task 串行访问两个设备，可天然避免总线并发；若未来拆分为多个独立采集任务，则必须增加总线互斥，并以完整 I2C transaction 为互斥范围。

---

## 9. 数据发送需求

传感器采集数据统一通过项目现有 UART 功能发送至 PC 串口助手。

应复用已有：

- UART Platform；
- UART Service；
- DMA；
- RingBuffer；
- FreeRTOS 通信结构。

不得为传感器数据另建绕过现有 UART 架构的发送链路。

第一阶段使用易于人工观察的文本数据格式，例如：

```text
ENV,T=25.34,H=62.18\r\n
IMU,AX=0.013,AY=-0.021,AZ=0.998,GX=0.12,GY=-0.42,GZ=0.08\r\n
```

若实现 Roll / Pitch，可增加：

```text
ATT,ROLL=-1.24,PITCH=2.36\r\n
```

第一阶段不强制实现自定义二进制帧协议。

---

## 10. UART 接收链路要求

PC 控制命令必须复用现有 UART DMA + RingBuffer 接收能力。

推荐数据流：

```text
UART DMA RX
    -> RingBuffer
    -> Command Parser
    -> APP Control Event
    -> APP Acquisition State Machine
```

UART Service 只负责通信能力，不直接执行传感器启停、LED 控制等业务逻辑。

命令解析和业务控制必须位于更高层。

---

## 11. 推荐任务组织

第一阶段优先采用较简单的任务模型：

- Communication Task：处理 UART 接收、RingBuffer 数据及命令解析；
- Sensor Task：根据 APP 状态和各自采样周期串行完成 DHT20 / MPU6050 采集；
- Button 处理可由独立任务、周期服务或既有系统调度方式实现。

Sensor Task 内部根据不同时间基准分别判断 DHT20 和 MPU6050 是否到达采样时间，不要求两个设备使用相同周期。

若后续确有必要，可再拆分 Environment Task 与 Motion Task，并为软件 I2C 增加总线互斥。

---

## 12. 分层边界

最终推荐职责如下：

```text
APP
├── 系统采集状态机
├── 控制事件处理
├── 数据组织
└── Communication 协调

Service
├── UART Service
├── Log Service
├── Button Service
├── Environment Service
└── Motion Service

Platform
├── GPIO Platform
├── Soft I2C
├── DHT20 BSP
├── MPU6050 BSP
└── UART Platform

Impl
├── STM32 GPIO 实现
├── STM32 UART 实现
├── RTOS 实现
└── 其他与具体平台绑定的实现
```

APP 可以依赖 Service 和 Platform 的公开能力，但不得直接依赖 Impl。

Service 不应绕过 Platform 直接调用 STM32 HAL。

## 13. 第一阶段范围冻结

### 必须完成

- GPIO Platform / Impl；
- LED 控制；
- 按键输入；
- 按键消抖；
- 单击、双击、长按识别；
- 软件 I2C；
- DHT20 驱动与温湿度采集；
- MPU6050 驱动与六轴原始数据采集；
- APP 采集状态机；
- 按键控制启停和单次采样；
- UART `START / STOP / ONCE / STATUS / HELP` 控制；
- 周期采集；
- 复用现有 UART DMA + RingBuffer 数据链路向 PC 输出数据；
- 基础日志与错误反馈。

### 可选扩展

- MPU6050 Roll / Pitch 姿态计算；
- 更丰富的状态查询；
- 参数配置命令；
- 更严格的 UART 应用层协议。

### 当前暂停

- SPI Platform / Impl；
- SPI LCD 显示；
- GUI；
- W25Q64；
- AT24C02；
- 蓝牙；
- 复杂姿态融合；
- 长期稳定 Yaw 解算。

## 14. 最终验收场景

### 场景 1：启动

1. 系统上电；
2. 初始化完成；
3. LED 熄灭；
4. 不周期输出传感器数据；
5. UART 可以正常接收控制命令。

### 场景 2：按键启动

1. `STOPPED` 状态下单击按键；
2. LED 点亮；
3. 系统进入 `RUNNING`；
4. DHT20 / MPU6050 按各自周期采样；
5. PC 串口助手持续收到传感器数据。

### 场景 3：按键停止

1. `RUNNING` 状态下长按按键 >= 3 s；
2. 周期采集停止；
3. LED 熄灭；
4. 系统进入 `STOPPED`。

### 场景 4：按键单次采样

1. `STOPPED` 状态下双击；
2. DHT20 与 MPU6050 各采集一次；
3. PC 收到一次完整数据；
4. LED 不亮；
5. 系统保持 `STOPPED`。

### 场景 5：UART 启动与停止

1. PC 发送 `START`；
2. 系统进入 `RUNNING` 且 LED 点亮；
3. PC 持续收到传感器数据；
4. PC 发送 `STOP`；
5. 周期采集停止且 LED 熄灭。

### 场景 6：UART 单次采样

1. 系统处于 `STOPPED`；
2. PC 发送 `ONCE`；
3. 两个传感器各采集一次；
4. PC 收到一次数据；
5. 系统保持 `STOPPED`。

### 场景 7：控制入口一致性

无论状态由按键还是 UART 改变：

- APP 内部只能存在一个真实采集状态；
- LED 状态必须与周期采集状态一致；
- 不允许按键和 UART 分别维护独立状态。

## 15. 项目最终闭环

```text
KEY -------------------------+
                              |
                              v
                       APP Control FSM
                              ^
                              |
PC -> UART RX -> RingBuffer -> Command Parser
                              |
                              v
                         Sensor Task
                         /         \
                      DHT20       MPU6050
                         \         /
                          Soft I2C
                              |
                        Platform GPIO

Sensor Data
    -> APP / Communication
    -> UART Service
    -> UART DMA TX
    -> PC Serial Assistant

APP Control FSM
    -> LED
```

完成上述闭环后，本项目的核心目标即视为完成。SPI/LCD 等功能作为后续独立扩展阶段处理，不纳入当前最终验收范围。
