# 最终功能需求

> 状态：Final Baseline  
> 更新时间：2026-09-04

## 1. 文档目的

本文档收束 `stm32f4_DMA_UART_ring_RTOS` 的最终综合实现范围，是当前产品业务行为的权威需求基线。

当前目标：完成一个基于 FreeRTOS 的稳定数据采集系统，可通过本地按键与 PC UART 指令统一控制 DHT20 + MPU6050 采集，通过 USART1 DMA 上报数据，并通过 RTT / EasyLogger 完成诊断。

最终软件实现阶段已经收束为：

```text
Phase 9 — Final RTOS Application Integration
```

不再保留独立 Phase 10。Phase 9 完成并通过最终综合板测后，本项目核心目标视为完成。

---

## 2. 最终硬件组成

```text
MCU        : STM32F411CEU6
DHT20      : temperature / relative humidity
MPU6050    : accel XYZ + gyro XYZ
Button     : PA0
LED        : PC13
UART       : USART1 / 115200 8N1
Soft I2C   : PB6 SCL / PB7 SDA
RTOS       : CMSIS-RTOS2 + FreeRTOS
Log        : EasyLogger + SEGGER RTT
```

DHT20 与 MPU6050 共用 PB6/PB7 Software I2C。

Software I2C 基于 Platform GPIO，不使用 STM32 硬件 I2C 外设。

---

## 3. 系统默认状态

系统启动并完成初始化后：

```text
APP State            = STOPPED
LED                  = OFF
UART RX              = ACTIVE
RTT Log              = ACTIVE
Periodic Acquisition = DISABLED
```

要求：

- DHT20 / MPU6050 不进行周期采集；
- UART 接收始终可工作；
- RTT / EasyLogger 始终可用于诊断；
- APP Control FSM 是 STOPPED / RUNNING 的唯一真实状态源。

允许存在：

```text
onceActive
onceSource
```

作为一次性业务 operation context，但它们不是第三个 APP 业务状态。

---

## 4. 统一控制事件

Button 与 UART 最终都转换为：

```text
APP_CTRL_START
APP_CTRL_STOP
APP_CTRL_SAMPLE_ONCE
APP_CTRL_GET_STATUS
```

事件来源附加：

```text
APP_CTRL_SOURCE_BUTTON
APP_CTRL_SOURCE_UART
```

来源只影响是否需要 UART command response，不允许形成第二份 running 状态。

---

## 5. 按键控制需求

### 5.1 手势参数

```text
PROJECT_BUTTON_SAMPLE_PERIOD_MS = 10 ms
PROJECT_BUTTON_DEBOUNCE_MS      = 30 ms
PROJECT_BUTTON_DOUBLE_CLICK_MS  = 300 ms
PROJECT_BUTTON_LONG_PRESS_MS    = 3000 ms
```

Button active LOW / Pull-Up。

单击必须等待双击窗口结束后再确认。

### 5.2 事件映射

```text
SINGLE -> APP_CTRL_START
DOUBLE -> APP_CTRL_SAMPLE_ONCE
LONG   -> APP_CTRL_STOP
```

### 5.3 业务行为

STOPPED 且无 ONCE：

```text
SINGLE -> START -> RUNNING
DOUBLE -> SAMPLE_ONCE -> remain STOPPED
LONG   -> no business action
```

RUNNING：

```text
SINGLE -> remain RUNNING
DOUBLE -> no extra acquisition
LONG   -> STOP -> STOPPED
```

STOPPED 且 ONCE 正在执行：

```text
SINGLE / DOUBLE / LONG
 -> ignore business action
 -> optional RTT summary
```

按键轮询由 Control Task 承担，不建立独立 Button Task。

---

## 6. LED 状态需求

```text
STOPPED                -> OFF
RUNNING                -> ON
RUNNING periodic TX    -> keep ON
ONCE TX SUCCESS        -> blink 3 times -> OFF
ONCE sample/TX failure -> keep OFF
```

成功闪烁：

```text
100 ms ON / 100 ms OFF / 3 times
```

只有完整 ONCE 业务成功后才允许触发 `ONCE_SUCCESS`。

Indicator Task 独立执行当前阻塞式闪烁，因此不能阻塞 Control / Communication / Acquisition。

第一版接受：ONCE 闪烁期间若 START 到达，RUNNING LED 呈现最多延迟约一次闪烁周期；APP 业务状态必须立即由 Control FSM 更新。

---

## 7. UART 控制需求

严格命令：

```text
START\r\n
STOP\r\n
ONCE\r\n
STATUS\r\n
HELP\r\n
```

协议：

```text
strict CRLF
uppercase only
case-sensitive
no trim
no arguments
fixed-size storage
```

RingBuffer read boundary 不是 command boundary，必须支持 fragmented / coalesced byte chunks。

### 7.1 正常状态矩阵

| 命令 | STOPPED | RUNNING |
| --- | --- | --- |
| START | 进入 RUNNING，`OK START` | 保持 RUNNING，`ERR ALREADY_RUNNING` |
| STOP | 保持 STOPPED，`ERR ALREADY_STOPPED` | 进入 STOPPED，`OK STOP` |
| ONCE | 执行一次完整采集/发送，保持 STOPPED | 不额外采样，`ERR ALREADY_RUNNING` |
| STATUS | `STATUS STOPPED` | `STATUS RUNNING` |
| HELP | 返回命令列表 | 返回命令列表 |

### 7.2 ONCE active

ONCE 执行过程中业务状态仍是 STOPPED。

UART：

```text
START  -> ERR BUSY\r\n
STOP   -> ERR BUSY\r\n
ONCE   -> ERR BUSY\r\n
STATUS -> STATUS STOPPED\r\n
HELP   -> normal HELP response
```

### 7.3 产品响应

```text
OK START\r\n
OK STOP\r\n
ERR ALREADY_RUNNING\r\n
ERR ALREADY_STOPPED\r\n
ERR BUSY\r\n
ERR ACQUISITION_FAILED\r\n
STATUS RUNNING\r\n
STATUS STOPPED\r\n
```

Communication-local：

```text
HELP START STOP ONCE STATUS HELP\r\n
ERR UNKNOWN_COMMAND\r\n
ERR COMMAND_TOO_LONG\r\n
```

成功 ONCE 不强制追加 `OK ONCE`；完整 sensor report TX 成功本身即成功业务输出。

## 8. 周期采集需求

完整采集周期与 UART 上报周期统一：

```text
PROJECT_ACQUISITION_PERIOD_MS = 2000U
```

START 行为冻结：

```text
START
 -> immediate first DHT20 + MPU6050 acquisition/report
 -> then every 2000 ms
```

RUNNING：

```text
DHT20
 -> MPU6050
 -> complete acquisition result
 -> Communication Task
 -> UART report
```

周期必须按绝对 deadline 推进：

```text
nextDeadline += 2000 ms
```

不能把传感器执行时间不断累加进周期，也不能在超期后连续 catch-up 补采历史样本。

STOPPED 不进行周期采集。

---

## 9. Unified Acquisition Service 需求

Phase 9 建立统一 Acquisition Service，组合已经验证的 Platform DHT20 与 MPU6050。

职责：

```text
DHT20 read
 -> MPU6050 read
 -> one complete acquisition result
```

不负责：

```text
START / STOP / ONCE decision
2 s scheduling
Task / Queue
UART
LED
shared Software I2C lifecycle
```

### 9.1 成功语义

```text
DHT20 success
AND MPU6050 success
= complete acquisition success
```

任一失败，整个采集业务失败。

### 9.2 诊断语义

即使 DHT20 失败，也继续尝试 MPU6050，以帮助区分：

```text
single-device failure
shared Software I2C / bus failure
```

### 9.3 输出原子性

使用局部 temporary result。

只有两个传感器都成功才一次性提交 caller output。

失败时 caller 原有 acquisition data 不得被半成品覆盖。

## 10. DHT20 / MPU6050 数据需求

### 10.1 DHT20

```text
temperature
relative humidity
```

DHT20 已实现为 Platform lightweight sensor capability，共享 `platform_i2c_t`，不拥有总线生命周期。

### 10.2 MPU6050

第一版：

```text
Accel X/Y/Z raw + g
Gyro X/Y/Z raw + deg/s
```

不实现：

```text
Roll
Pitch
Yaw
Complementary Filter
Kalman Filter
DMP
复杂姿态融合
```

MPU6050 同样只引用共享 Software I2C。

---

## 11. Software I2C 并发需求

Software I2C 已完成并冻结：

```text
Master-only
7-bit
synchronous
Platform GPIO based
microsecond timing
no internal mutex
```

第一版只有 Acquisition Task 运行时访问 DHT20 / MPU6050：

```text
DHT20 complete transaction
 -> MPU6050 complete transaction
```

因此不增加 I2C Mutex。

只有未来出现真实第二个并发访问者时，才讨论 transaction-level synchronization。

同步 sensor transaction 不要求被 STOP 中途强制取消。

STOP 到达 active transaction 时允许安全收尾，但 STOP 生效后不得继续产生新的 periodic acquisition；在结果发布前若观察到 pending STOP，应丢弃 stale periodic result。

---

## 12. UART 数据发送需求

传感器数据必须复用唯一正式链：

```text
Communication Task
 -> UART Service
 -> Platform UART async TX
 -> STM32 UART Impl
 -> DMA2_Stream7
 -> USART1
 -> PC
```

禁止另建 UART TX 旁路。

Communication Task 是唯一产品 TX requester。

第一版文本格式：

```text
ENV,T=25.34,H=62.18\r\n
IMU,AX=0.013,AY=-0.021,AZ=0.998,GX=0.12,GY=-0.42,GZ=0.08\r\n
```

`service_uart_write()` 返回后，DMA 不得继续访问 caller TX buffer。

UART RX DMA 与 TX DMA 必须允许同时工作。

---

## 13. ONCE 完整事务需求

STOPPED 且没有 active ONCE：

```text
SAMPLE_ONCE
 -> onceActive = true
 -> DHT20 read
 -> MPU6050 read
 -> complete report
 -> UART TX
```

成功定义：

```text
DHT20 OK
AND MPU6050 OK
AND complete UART report TX OK
```

成功后：

```text
onceActive = false
 -> Indicator ONCE_SUCCESS
 -> blink 3 times
 -> OFF
 -> remain STOPPED
```

Acquisition failure：

```text
onceActive = false
no success blink
RTT diagnostic
UART source may receive ERR ACQUISITION_FAILED
```

UART TX failure：

```text
onceActive = false
no success blink
RTT diagnostic
```

如果 UART transport 本身失败，不要求再通过同一失败通道发送 `ERR TX_FAILED`。

---

## 14. 最终 RTOS 任务组织

固定 4 个产品业务 Task：

| Task | Initial Stack | Priority | Responsibility |
| --- | ---: | --- | --- |
| Communication Task | 2048 B | ABOVE_NORMAL | UART RX parser + sole product TX |
| Control Task | 1024 B | ABOVE_NORMAL | Button polling + sole APP Control FSM |
| Acquisition Task | 1536 B | NORMAL | periodic/ONCE sensor execution |
| Indicator Task | 768 B | BELOW_NORMAL | LED semantic execution |

这些资源是第一版宽松 bring-up baseline。

系统完整稳定运行后记录 stack high-water mark 和 Queue peak occupancy，再决定是否缩小。

当前不把功耗作为 Phase 9 设计目标，不引入 Tickless Idle / Button EXTI wake。

### 14.1 CubeMX defaultTask

CubeMX 自动生成 `defaultTask` 当前无法删除。

它不属于产品任务。

实现时仅在 USER CODE 中首次运行后：

```c
(void)argument;
osThreadExit();
```

不得把 defaultTask 改造成上述四个产品 Task 中的任意一个。

FreeRTOS Idle / Timer Service Task 属于内核资源，不计入产品 Task 数量。

## 15. APP IPC 需求

第一版 Queue：

```text
Control Queue                 depth 8
Acquisition Command Queue     depth 4
Communication Outbound Queue  depth 8
Indicator Queue               depth 4
```

要求：

```text
Platform Queue
bounded
copy-by-value
no temporary caller stack pointer
no infinite producer blocking
queue-full observable
```

第一版不增加：

```text
APP state mutex
Queue Set
Event Group for business orchestration
extra worker Task
```

Communication Outbound Queue 不能直接唤醒 UART Service private notify wait，第一版允许 Communication Task 使用约 20 ms timeout 周期检查 outbound Queue；当前不为此做低功耗优化。

---

## 16. RTT / EasyLogger 日志需求

职责：

```text
USART1 -> product control + product data
RTT    -> initialization / state / acquisition / diagnostics / errors
```

建议：

```text
INFO  -> initialization / START / STOP / ONCE / state change
DEBUG -> acquisition/report summary
WARN  -> recoverable I2C / Sensor / UART / Queue issue
ERROR -> initialization / critical runtime failure
```

禁止正常运行逐 I2C bit / ACK、逐 UART byte、逐 DMA step、逐 Button polling 刷日志。

ISR / HAL Callback 不进行大量格式化日志。

---

## 17. 分层与 ISR 边界

```text
APP -> Service       ALLOWED
APP -> Platform      ALLOWED
Service -> Platform  ALLOWED
Platform -> Impl     ALLOWED
APP -> Impl          FORBIDDEN
Service -> Impl      FORBIDDEN
```

APP / Service 不得直接依赖 HAL、CubeMX Handle 或 Impl 私有接口。

ISR / HAL Callback 只允许：

```text
capture
necessary copy
lightweight state update
ISR-safe notify
quick exit
```

禁止 ISR：

```text
Button gesture FSM
Software I2C transaction
full protocol parser
Sensor business
LED blocking blink
malloc/free
ordinary mutex
heavy formatted log
```

## 18. 最终验收场景

### 场景 1：启动

- 上电初始化成功；
- STOPPED；
- LED OFF；
- UART RX ACTIVE；
- RTT 可观察初始化；
- 不周期发送 sensor report。

### 场景 2：按键启动

- STOPPED SINGLE；
- APP RUNNING；
- LED ON；
- 立即完成第一组 DHT20 + MPU6050 report；
- 后续每 2 s 一组完整 report。

### 场景 3：按键停止

- RUNNING LONG >= 3 s；
- APP STOPPED；
- LED OFF；
- 不再产生新的周期 report；
- active sensor transaction 可安全收尾但不得产生 STOP 后 stale report。

### 场景 4：按键 ONCE

- STOPPED DOUBLE；
- 两个传感器各执行一次；
- PC 收到一次完整 report；
- UART TX 成功后 LED 闪 3 次；
- 保持 STOPPED。

### 场景 5：UART 控制

- `START / STOP / ONCE / STATUS / HELP` 正确；
- fragmented / coalesced command 正确；
- UART 和 Button 使用同一个 APP state truth；
- ONCE active 的 BUSY / STATUS 语义正确。

### 场景 6：UART DMA

- USART1 RX 在 TX DMA active 时仍保持接收；
- RX = DMA2_Stream2 Circular；
- TX = DMA2_Stream7 Normal；
- 不存在 direct HAL product TX bypass。

### 场景 7：异常

以下异常必须可通过 RTT 观察，不得静默失败：

```text
I2C NACK / bus failure
DHT20 status / CRC failure
MPU6050 WHO_AM_I / read failure
UART / DMA failure
RingBuffer overflow
important Queue submission failure
```

ONCE acquisition/TX 失败时不得执行成功闪烁。

### 场景 8：资源

最终系统完整运行后记录：

```text
4 product Task stack high-water marks
4 APP Queue peak/observed occupancy
```

第一轮目标是确认资源足够，不以压缩资源为验收前置条件。
