# 最终功能需求

## 1. 文档目的

本文档用于收束 `stm32f4_DMA_UART_ring_RTOS` 项目的最终综合实现范围，作为后续 GPIO、软件 I2C、传感器、按键事件、APP 状态机、日志及串口联调的统一功能基线。

本阶段不继续扩展 SPI/LCD、外部 Flash 等外围功能，优先完成一个可稳定运行、可通过本地按键和 PC 串口指令控制的数据采集闭环。

---

## 2. 最终硬件组成

- MCU：STM32F411
- 温湿度传感器：DHT20
- 六轴惯性传感器：MPU6050
- 用户按键：1 个
- 状态 LED：1 个
- PC：通过 UART 串口助手进行控制与数据显示

DHT20 与 MPU6050 共用一条软件 I2C 总线。

软件 I2C 基于 GPIO 模拟实现，不使用 STM32 硬件 I2C 外设。

---

## 3. 系统默认状态

系统启动并完成初始化后：

- 数据采集功能默认关闭；
- LED 默认熄灭；
- DHT20 不进行周期采集；
- MPU6050 不进行周期采集；
- UART 接收功能保持工作，可随时接收 PC 端控制指令；
- RTT / EasyLogger 日志功能保持正常工作。

系统逻辑状态至少包括：

- `STOPPED`：周期采集关闭；
- `RUNNING`：周期采集开启。

APP 层作为采集状态的唯一维护者，按键和 UART 命令只产生控制事件，不直接操作传感器状态。

---

## 4. 按键控制需求

### 4.1 短按一次

当系统处于 `STOPPED` 状态时：

- 单击按键；
- 系统进入 `RUNNING` 状态；
- LED 常亮；
- 启动 DHT20 与 MPU6050 周期采集；
- 系统每 5 s 完成一次传感器采集并通过现有 UART 发送链路将本次数据发送至 PC 串口助手。

当系统已经处于 `RUNNING` 状态时，单击不改变系统状态。

### 4.2 长按

当按键持续按下时间达到或超过 3 s，且系统处于 `RUNNING` 状态时：

- 停止周期采集；
- 系统进入 `STOPPED` 状态；
- LED 熄灭。

当系统已经处于 `STOPPED` 状态时，长按不执行额外操作。

### 4.3 双击

当系统处于 `STOPPED` 状态时：

- 在双击判定时间窗内连续短按两次；
- DHT20 采集一次；
- MPU6050 采集一次；
- 将本次采集结果通过 UART 发送至 PC；
- UART 发送成功后 LED 闪烁 3 次；
- 闪烁完成后 LED 恢复熄灭；
- 系统始终保持 `STOPPED` 状态。

当系统处于 `RUNNING` 状态时，双击不执行额外单次采集。

若本次传感器采集失败或 UART 发送失败，则 LED 不执行 3 次闪烁成功提示，并通过 RTT 日志记录异常。

### 4.4 单击与双击判定

由于双击包含第一次短按，单击事件不得在第一次释放后立即执行。

按键服务应设置双击判定时间窗，在时间窗结束后再确认单击；若时间窗内出现第二次有效短按，则产生双击事件。

具体判定时间、消抖时间等参数应放入配置层统一管理，不在业务代码中散布魔法数字。

---

## 5. LED 状态指示需求

LED 用于表示数据采集状态以及单次采集发送成功反馈。

### 5.1 周期采集状态

- `STOPPED`：LED 常灭；
- `RUNNING`：LED 常亮；
- `RUNNING` 状态下每 5 s 的正常周期数据发送不改变 LED 常亮状态，不额外闪烁。

### 5.2 单次采集状态

当系统处于 `STOPPED` 状态并执行一次性采集时：

1. 采集期间 LED 保持熄灭；
2. DHT20 与 MPU6050 数据采集成功；
3. 数据通过 UART 发出；
4. 确认 UART 发送成功后 LED 闪烁 3 次；
5. 闪烁完成后 LED 恢复熄灭。

推荐闪烁节奏约为：亮 100 ms / 灭 100 ms，共 3 次。具体时序参数放入配置层管理。

APP 只表达“常亮、熄灭、闪烁 3 次”等业务语义，不应直接处理 LED 有效电平等底层细节。

对于 DMA 发送，优先以 UART TX Complete 事件作为“发送成功”的严格判据；若第一阶段现有 UART 架构暂未向 APP 暴露发送完成事件，可临时以 DMA 发送请求成功提交作为发送成功判据，但应在实现文档中明确说明。

## 6. UART 控制需求

PC 串口助手可以通过 UART 向设备发送文本命令。

第一阶段定义以下基础命令：

```text
START\r\n
STOP\r\n
ONCE\r\n
STATUS\r\n
HELP\r\n
```

### 6.1 START

- `STOPPED` 状态：进入 `RUNNING`，LED 常亮并开始周期采集；
- `RUNNING` 状态：保持当前状态，并返回已处于运行状态的信息。

### 6.2 STOP

- `RUNNING` 状态：停止周期采集，进入 `STOPPED`，LED 熄灭；
- `STOPPED` 状态：保持当前状态，并返回已停止的信息。

### 6.3 ONCE

- `STOPPED` 状态：DHT20 与 MPU6050 各采集一次，将数据通过 UART 发送至 PC；发送成功后 LED 闪烁 3 次，完成后保持 `STOPPED`；
- `RUNNING` 状态：不执行额外采样，返回当前已经处于连续采集状态的信息。

### 6.4 STATUS

返回当前系统采集状态，例如：

```text
STATE=STOPPED\r\n
```

或：

```text
STATE=RUNNING\r\n
```

### 6.5 HELP

返回当前支持的基础控制命令列表。

## 7. 控制事件统一原则

按键和 UART 是两个不同的输入源，但不得分别维护两套业务状态。

推荐统一转换为 APP 控制事件：

```text
APP_CTRL_START
APP_CTRL_STOP
APP_CTRL_SAMPLE_ONCE
APP_CTRL_GET_STATUS
```

事件映射关系：

| 输入源 | 操作 | APP 控制事件 |
| --- | --- | --- |
| 按键 | 单击 | `APP_CTRL_START` |
| 按键 | 双击 | `APP_CTRL_SAMPLE_ONCE` |
| 按键 | 长按 >= 3 s | `APP_CTRL_STOP` |
| UART | `START` | `APP_CTRL_START` |
| UART | `STOP` | `APP_CTRL_STOP` |
| UART | `ONCE` | `APP_CTRL_SAMPLE_ONCE` |
| UART | `STATUS` | `APP_CTRL_GET_STATUS` |

最终由 APP 层状态机统一决定是否执行事件。

## 8. 传感器采集需求

第一阶段以基础数据采集为目标，不进行 MPU6050 姿态融合和 Roll / Pitch / Yaw 解算。

### 8.1 周期采集

系统处于 `RUNNING` 状态时：

- 每 5 s 执行一次完整采集周期；
- 每个采集周期读取一次 DHT20；
- 每个采集周期读取一次 MPU6050；
- 两个传感器采集完成后组织成一次业务数据报告；
- 通过现有 UART 发送链路发送至 PC 串口助手。

第一阶段将“采集周期”和“UART 上报周期”统一为 5 s，以降低系统复杂度。

后续如果加入姿态计算或高频运动采样，再将 MPU6050 采样周期和 UART 上报周期解耦，本阶段暂不实现。

### 8.2 DHT20

采集内容：

- 温度；
- 相对湿度。

### 8.3 MPU6050

第一阶段必须采集：

- Accel X；
- Accel Y；
- Accel Z；
- Gyro X；
- Gyro Y；
- Gyro Z。

建议在基础驱动中同时保留原始值，并提供简单物理量换算，例如：

- 加速度：raw -> g；
- 角速度：raw -> deg/s。

第一阶段明确不实现：

- Roll；
- Pitch；
- Yaw；
- 互补滤波；
- 卡尔曼滤波；
- DMP；
- 复杂姿态融合。

---

## 9. 软件 I2C 需求

软件 I2C 基于现有 GPIO Platform 能力实现。

基本能力至少包括：

- START；
- STOP；
- ACK / NACK；
- Byte Write；
- Byte Read；
- 连续数据读写；
- 寄存器读写能力。

软件 I2C 协议逻辑不得直接依赖 STM32 HAL GPIO API，应通过 Platform GPIO 抽象访问 SCL 与 SDA。

软件 I2C 所需微秒级延时应通过独立延时能力实现，不直接使用阻塞时间过大的 RTOS 延时接口模拟位时序。

DHT20 与 MPU6050 共用同一条软件 I2C 总线。

第一阶段优先由单一 Sensor Task 串行访问两个设备，从任务组织上避免软件 I2C 总线并发。

若未来拆分为多个独立采集任务，则必须增加总线互斥，并以完整 I2C transaction 为互斥范围。

---

## 10. 数据发送需求

传感器采集数据统一通过项目现有 UART 功能发送至 PC 串口助手。

应复用已有：

- UART Platform；
- UART Service；
- DMA；
- RingBuffer；
- FreeRTOS 通信结构。

不得为传感器数据另建绕过现有 UART 架构的发送链路。

第一阶段使用易于人工观察的文本数据格式，例如：

```text
ENV,T=25.34,H=62.18\r\n
IMU,AX=0.013,AY=-0.021,AZ=0.998,GX=0.12,GY=-0.42,GZ=0.08\r\n
```

第一阶段不发送 Roll / Pitch / Yaw 数据，也不强制实现自定义二进制帧协议。

系统处于 `RUNNING` 状态时，每 5 s 发送一次完整传感器数据报告。

---

## 11. UART 接收链路要求

PC 控制命令必须复用现有 UART DMA + RingBuffer 接收能力。

推荐数据流：

```text
UART DMA RX
    -> RingBuffer
    -> Command Parser
    -> APP Control Event
    -> APP Acquisition State Machine
```

UART Service 只负责通信能力，不直接执行传感器启停、LED 控制等业务逻辑。

命令解析和业务控制必须位于更高层。

日志应记录完整 UART 命令或完整业务发送事件，不应默认逐字节打印 UART RX/TX 数据。

---

## 12. RTT / EasyLogger 日志需求

RTT / EasyLogger 用于系统内部运行状态、调试和故障诊断；UART 串口助手用于业务数据和控制命令，两者职责分离。

```text
UART -> 产品/业务数据与控制
RTT  -> 初始化状态、运行状态、采集状态、收发状态和异常诊断
```

### 12.1 初始化过程

系统初始化过程应通过 RTT 日志展示主要模块状态，包括但不限于：

- System init start；
- GPIO init；
- Soft I2C init；
- DHT20 init；
- MPU6050 init / WHO_AM_I 检查；
- UART / Communication init；
- Log Service init；
- APP / Service init；
- System ready；
- 初始采集状态 `STOPPED`。

关键模块初始化成功可使用 `INFO`；初始化失败使用 `ERROR`。

### 12.2 采集过程

日志应展示关键业务状态，而不是记录每一个 I2C 位操作或寄存器访问。

推荐：

- `INFO`：START / STOP / ONCE 事件、采集状态变化；
- `DEBUG`：每 5 s 采集完成、传感器数据摘要；
- `WARN / ERROR`：DHT20 / MPU6050 读取失败、I2C NACK、设备异常。

正常软件 I2C 的 START、STOP、ACK、每个 Byte 默认不得持续打印日志；这类细节只用于临时底层调试。

### 12.3 UART 收发过程

推荐记录：

- 收到完整控制命令；
- 命令解析结果；
- 完整传感器报告提交发送；
- UART DMA TX complete；
- RingBuffer overflow；
- UART / DMA 异常。

不推荐在正常运行模式下逐字节打印 RX/TX 数据。

### 12.4 日志等级建议

| 日志等级 | 典型内容 |
| --- | --- |
| INFO | 初始化结果、START/STOP/ONCE、状态切换、完整命令 |
| DEBUG | 每 5 s 采集结果摘要、UART 数据报告发送完成、LED 单次成功提示 |
| WARN | I2C NACK、传感器单次读取失败、可恢复通信异常 |
| ERROR | 初始化失败、关键设备不可用、UART/DMA 严重错误 |

关闭 DEBUG 后，仍应能够通过 INFO/WARN/ERROR 看清系统主要生命周期和异常状态。

### 12.5 中断日志约束

UART DMA / IDLE 等 ISR 或 HAL 中断回调中不得进行大量 EasyLogger 格式化和 RTT 输出。

推荐流程：

```text
ISR / HAL Callback
    -> 更新最小状态或通知任务
    -> Task / Service 处理
    -> RTT Log
```

避免日志增加关键中断路径执行时间。

## 13. 推荐任务组织

第一阶段优先采用较简单的任务模型：

- Communication Task：处理 UART 接收、RingBuffer 数据及命令解析；
- Sensor Task：根据 APP 状态每 5 s 串行完成一次 DHT20 + MPU6050 采集并触发业务数据发送；
- Button 处理可由独立任务、周期服务或既有系统调度方式实现。

第一阶段不需要为 DHT20 与 MPU6050 建立不同采样周期，也不要求拆分 Environment Task 与 Motion Task。

若未来加入姿态计算或高频传感器采样，再重新拆分任务和周期，并为共享软件 I2C 增加必要的并发保护。

---

## 14. 分层边界

最终推荐职责如下：

```text
APP
├── 系统采集状态机
├── 控制事件处理
├── 数据组织
└── Communication 协调

Service
├── UART Service
├── Log Service
├── Button Service
├── Environment Service
└── Motion Service

Platform
├── GPIO Platform
├── Soft I2C
├── DHT20 BSP
├── MPU6050 BSP
└── UART Platform

Impl
├── STM32 GPIO 实现
├── STM32 UART 实现
├── RTOS 实现
└── 其他与具体平台绑定的实现
```

APP 可以依赖 Service 和 Platform 的公开能力，但不得直接依赖 Impl。

Service 不应绕过 Platform 直接调用 STM32 HAL。

UART Service 不应理解 START / STOP / ONCE 等业务语义。

## 15. 第一阶段范围冻结

### 必须完成

- GPIO Platform / Impl；
- LED 常亮、熄灭、闪烁 3 次基础行为；
- 按键输入；
- 按键消抖；
- 单击、双击、长按识别；
- 软件 I2C；
- DHT20 驱动与温湿度采集；
- MPU6050 初始化、WHO_AM_I 检查、六轴基础数据采集；
- MPU6050 原始值基础物理量换算；
- APP 采集状态机；
- 按键控制启停和单次采样；
- UART `START / STOP / ONCE / STATUS / HELP` 控制；
- `RUNNING` 状态每 5 s 完成一次采集并发送；
- 单次采集发送成功后 LED 闪烁 3 次；
- 复用现有 UART DMA + RingBuffer 数据链路向 PC 输出数据；
- RTT / EasyLogger 展示初始化、采集、UART 收发和异常状态；
- 基础错误反馈。

### 后续扩展

- MPU6050 Roll / Pitch / Yaw；
- 高频 MPU6050 采样；
- 采样周期与 UART 上报周期解耦；
- 互补滤波 / 卡尔曼滤波 / DMP；
- 更丰富的状态查询；
- 参数配置命令；
- 更严格的 UART 应用层协议。

### 当前暂停

- SPI Platform / Impl；
- SPI LCD 显示；
- GUI；
- W25Q64；
- AT24C02；
- 蓝牙；
- 复杂姿态融合。

## 16. 最终验收场景

### 场景 1：启动

1. 系统上电；
2. RTT 日志依次展示主要模块初始化状态；
3. 初始化完成后 LED 熄灭；
4. 系统状态为 `STOPPED`；
5. 不周期输出传感器业务数据；
6. UART 可以正常接收控制命令。

### 场景 2：按键启动

1. `STOPPED` 状态下单击按键；
2. RTT 输出 START 和状态切换日志；
3. LED 常亮；
4. 系统进入 `RUNNING`；
5. 每 5 s 读取一次 DHT20 与 MPU6050；
6. 每 5 s 向 PC 串口助手发送一次完整传感器数据；
7. RTT DEBUG 日志可看到采集和发送状态。

### 场景 3：按键停止

1. `RUNNING` 状态下长按按键 >= 3 s；
2. RTT 输出 STOP 和状态切换日志；
3. 周期采集停止；
4. LED 熄灭；
5. 系统进入 `STOPPED`。

### 场景 4：按键单次采样

1. `STOPPED` 状态下双击；
2. RTT 输出 ONCE 事件日志；
3. DHT20 与 MPU6050 各采集一次；
4. PC 收到一次完整数据；
5. UART 发送成功后 LED 闪烁 3 次；
6. LED 最终恢复熄灭；
7. 系统保持 `STOPPED`。

### 场景 5：UART 启动与停止

1. PC 发送 `START`；
2. RTT 输出收到完整命令及状态变化；
3. 系统进入 `RUNNING` 且 LED 常亮；
4. 每 5 s PC 收到一次传感器数据；
5. PC 发送 `STOP`；
6. RTT 输出收到完整命令及状态变化；
7. 周期采集停止且 LED 熄灭。

### 场景 6：UART 单次采样

1. 系统处于 `STOPPED`；
2. PC 发送 `ONCE`；
3. RTT 输出命令解析及单次采集状态；
4. 两个传感器各采集一次；
5. PC 收到一次完整数据；
6. UART 发送成功后 LED 闪烁 3 次；
7. LED 恢复熄灭；
8. 系统保持 `STOPPED`。

### 场景 7：异常

发生以下异常时应通过 RTT 输出 WARN 或 ERROR 日志：

- 软件 I2C NACK；
- DHT20 读取失败；
- MPU6050 WHO_AM_I 异常；
- MPU6050 读取失败；
- UART / DMA 发送失败；
- RingBuffer overflow。

单次采集或发送失败时，不执行 LED 闪烁 3 次的成功提示。

### 场景 8：控制入口一致性

无论状态由按键还是 UART 改变：

- APP 内部只能存在一个真实采集状态；
- LED 常亮/熄灭状态必须与周期采集状态一致；
- 不允许按键和 UART 分别维护独立状态。

## 17. 项目最终闭环

```text
KEY -------------------------+
                              |
                              v
                       APP Control FSM
                              ^
                              |
PC -> UART RX -> RingBuffer -> Command Parser
                              |
                              v
                         Sensor Task
                      every 5 seconds
                         /         \
                      DHT20       MPU6050
                         \         /
                          Soft I2C
                              |
                        Platform GPIO

Sensor Data
    -> APP / Communication
```
