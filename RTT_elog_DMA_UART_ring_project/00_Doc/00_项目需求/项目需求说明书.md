# UART DMA 环形缓冲通信项目需求说明书

**文档版本：** V0.1
**项目阶段：** 需求定义
**目标平台：** STM32F411CEU6 + FreeRTOS
**调试环境：** J-Link + RTT + EasyLogger

------

## 1. 项目背景

本项目最初来源于串口通信学习课程中的中阶实验，主要目标为：

- UART 不定长数据接收；
- DMA 串口收发；
- 环形缓冲区设计与使用。

在此基础上，项目进一步引入实际嵌入式软件工程中的分层设计、模块职责、并发控制、异常处理和测试验证方法，并按照：

```
APP → Service → Platform → Impl → Vendor
```

进行重新设计。

本项目仍以学习 UART、DMA、Ring Buffer 和 FreeRTOS 数据流设计为核心，不以构建通用嵌入式软件框架为目标。

------

# 2. 项目目标

## 2.1 核心功能目标

系统应实现基于 UART + DMA 的可靠串口通信机制，包括：

1. UART DMA 不定长数据接收；
2. UART DMA 数据发送；
3. DMA 接收数据向软件 Ring Buffer 转移；
4. FreeRTOS 任务异步处理接收数据；
5. 正确处理连续数据、突发数据和不定长数据；
6. 支持缓冲区状态、通信错误和数据统计；
7. RTT + EasyLogger 独立承担调试日志输出；
8. 保证业务 UART 与调试日志通道相互独立。

------

## 2.2 工程训练目标

通过本项目训练以下实际工程能力：

- 软件需求分析；
- 分层架构设计；
- Platform 硬件抽象接口设计；
- Impl 与 HAL 的隔离；
- ISR、Callback、Task 数据流设计；
- Ring Buffer 并发模型设计；
- 错误处理与恢复机制；
- 模块运行数据建模；
- 接口设计；
- 单元测试和集成测试；
- Debug 和性能测试。

------

## 2.3 非目标

本项目第一阶段不要求实现：

- 通用跨平台驱动框架；
- 运行时动态选择 MCU Backend；
- UART 通用设备管理框架；
- 完整通信协议栈；
- OTA、Ymodem 等升级协议；
- CLI/Shell；
- 动态内存管理；
- 复杂消息总线；
- 多级事件框架；
- 通用 DMA 抽象层；
- 通用 IRQ 抽象层；
- 零拷贝通信框架。

只有当后续需求实际出现时，再增加相应设计。

# 4. UART 功能需求

## UART-RX-001 DMA接收

业务 UART 应使用 DMA 完成正常数据接收。

正常数据接收过程中，不应由 CPU 对每个 UART 字节执行轮询读取。

------

## UART-RX-002 不定长接收

系统必须支持不定长 UART 数据。

接收数据长度不要求与 DMA Buffer 长度一致。

STM32 实现层允许采用：

```
UART + DMA + IDLE
```

或 STM32 HAL 等价的不定长 DMA 接收机制。

------

## UART-RX-003 连续接收

系统必须支持多个数据块连续到达。

处理上一批数据时，不得因为软件流程设计错误导致 UART 接收长期停止。

------

## UART-RX-004 DMA接收缓冲

Impl 层应维护 DMA RX Buffer。

DMA Buffer 属于底层硬件数据搬运缓冲，不作为业务数据长期存储区。

------

## UART-RX-005 Ring Buffer

UART Service 应使用 Ring Buffer 保存已经从 DMA 接收到、但尚未被业务处理的数据。

数据流原则为：

UART
→ DMA
→ DMA RX Buffer
→ UART事件
→ Ring Buffer
→ Service Task
→ APP

DMA Buffer 和 Ring Buffer 必须具有明确不同的职责。

------

## UART-TX-001 DMA发送

UART 数据发送应支持 DMA 模式。

正常发送过程中不得使用逐字节轮询方式占用 CPU。

------

## UART-TX-002 发送状态

当 UART DMA 正在发送时，应存在明确的 Busy 状态。

第一阶段不要求实现通用 TX Queue。

新的发送请求在底层仍处于 Busy 状态时，应：

- 返回明确 BUSY 状态；

而不是：

- 无限等待；
- 静默覆盖正在发送的数据。

------

## UART-TX-003 发送完成

DMA TX 完成后，应产生发送完成事件或更新发送状态。

上层不得直接依赖 STM32 HAL Callback。

------

# 5. Ring Buffer需求

## RB-001 基本功能

Ring Buffer 至少支持：

- 初始化；
- 写入；
- 读取；
- 查询已用空间；
- 查询剩余空间；
- 判断空；
- 判断满。

------

## RB-002 数据类型

第一阶段 Ring Buffer 按字节流设计：

```
uint8_t
```

不绑定具体通信协议。

------

## RB-003 静态内存

Ring Buffer 内存应采用静态分配。

正常运行过程中不得依赖 `malloc/free`。

------

## RB-004 数据顺序

Ring Buffer 必须保证 FIFO：

先写入的数据必须先被读取。

------

## RB-005 溢出策略

Ring Buffer 空间不足时，默认采用：

**保留未处理旧数据，丢弃无法写入的新数据。**

禁止静默覆盖未读取数据。

同时必须记录：

- Overflow 状态；
- Overflow 次数；
- 丢失字节数。

允许执行部分写入：

例如：

Ring Buffer 剩余 20 Byte
收到 50 Byte

则：

- 写入 20 Byte；
- 丢弃 30 Byte；
- dropped_bytes += 30；
- 设置 Overflow 标志。

------

# 6. FreeRTOS任务与数据流

## RTOS-001 ISR职责

UART/DMA ISR 或 HAL Callback 中只允许执行短时间、确定性操作。

允许：

- 获取接收长度；
- 更新简单状态；
- 将数据放入 Ring Buffer；
- 发送 Task Notification / Semaphore；
- 更新简单计数器。

原则上禁止：

- 长时间循环处理；
- 数据协议解析；
- 阻塞等待；
- `vTaskDelay()`；
- 动态内存申请；
- 大量日志打印；
- 执行业务逻辑。

------

## RTOS-002 UART接收任务

系统应至少存在一个负责 UART RX 数据处理的任务。

任务基本流程：

UART RX Event
→ Ring Buffer 写入
→ 通知 UART Service Task
→ Task 读取 Ring Buffer
→ 执行业务处理

------

## RTOS-003 空闲行为

UART Service Task 在无数据时不得持续轮询 Ring Buffer。

应使用：

- Task Notification；
- Semaphore；
- Event；

等 RTOS 同步机制进入阻塞状态。

------

## RTOS-004 ISR与Task关系

第一阶段 RX Ring Buffer 推荐采用：

**Single Producer / Single Consumer**

即：

Producer：
UART RX Callback / ISR路径

Consumer：
UART Service Task

不得允许多个模块未经设计同时修改 Ring Buffer 索引。

------

## RTOS-005 TX并发

若多个任务可能调用 UART TX，应由 UART Service 负责串行化。

第一阶段允许限定：

只有 UART Service 拥有业务 UART TX 权限。

------

# 7. RTT、EasyLogger和业务UART

## LOG-001 日志通道

调试日志默认使用：

EasyLogger
→ SEGGER RTT
→ J-Link

不得默认使用业务 UART 输出 Debug Log。

------

## LOG-002 通道隔离

业务 UART 和 Debug Log 必须逻辑隔离。

业务 UART：

用于被测试的数据通信。

RTT：

用于：

- Debug；
- Error；
- Warning；
- 状态观察；
- 性能统计。

------

## LOG-003 防止测试干扰

不得因为 EasyLogger 输出导致业务 UART：

- DMA TX 被占用；
- RX Buffer 被修改；
- 业务数据被插入日志内容。

------

## LOG-004 ISR日志限制

UART/DMA 高频 ISR 或 Callback 中禁止大量调用 EasyLogger。

必要错误信息优先：

- 设置错误标志；
- 增加错误计数器；

然后由 Task 上下文输出日志。

------

# 8. 异常与恢复要求

## ERR-001 Ring Buffer Overflow

出现 Ring Buffer Overflow 时系统不得：

- HardFault；
- 越界写；
- 修改未处理数据；
- 无限等待。

系统应：

1. 丢弃超出容量的新数据；
2. 设置 Overflow 状态；
3. 记录丢失字节数；
4. 允许系统继续运行。

------

## ERR-002 UART错误

至少应能够识别或记录 UART：

- Overrun；
- Framing Error；
- Noise Error；
- DMA异常；

等底层错误。

具体 STM32 Error Flag 只允许存在于 Impl 层。

------

## ERR-003 接收恢复

UART RX 出错后，应尝试恢复 DMA 接收。

不得因为一次通信异常永久停止 RX。

------

## ERR-004 超时

任何同步等待均不得无限阻塞。

如存在等待操作，应具有明确 Timeout。

------

## ERR-005 错误统计

UART Service Context 至少应支持统计：

- RX总字节数；
- TX总字节数；
- RX事件次数；
- TX完成次数；
- Overflow次数；
- Dropped Bytes；
- UART Error次数。

统计信息主要用于 Debug 和测试。

------

# 9. 数据模型要求

模块数据原则上分为：

## 9.1 Config

Config 表示初始化时确定、运行过程中通常保持不变的静态设置。

例如：

- Ring Buffer容量；
- 超时时间；
- UART逻辑实例；
- 最大处理数据长度。

------

## 9.2 Context

Context 表示模块运行过程中必须维护的内部状态。

例如：

- RX/TX统计；
- Ring Buffer对象；
- 当前UART状态；
- Overflow计数；
- Error计数；
- Task Handle；
- 同步对象。

------

## 9.3 Data

Data 表示模块向上层提供的业务数据。

对于当前 UART 字节流项目，不强制建立独立 Data Model。

如果未来增加：

- 帧解析；
- 协议包；
- 传感器数据；

再独立定义相应 Data 类型。

禁止为了形式完整而创建没有实际用途的数据模型。

------

# 10. 软件分层约束

项目采用：

```
APP → Service → Platform → Impl → Vendor
```

------

## 10.1 APP

APP负责：

- 项目业务流程；
- 测试场景；
- 功能组合。

APP不得直接调用：

- STM32 HAL；
- DMA；
- USART IRQ；
- UART_HandleTypeDef。

------

## 10.2 Service

UART Service负责：

- UART数据流管理；
- Ring Buffer；
- RX/TX状态；
- 超时；
- 数据统计；
- 并发控制；
- 向APP提供通信服务。

Service不得直接调用 STM32 HAL。

------

## 10.3 Platform

Platform负责声明与具体 MCU 无关的 UART 能力接口。

例如：

- UART初始化；
- 启动RX；
- 停止RX；
- DMA方式发送数据；
- UART事件通知。

Platform头文件中不得出现：

- `UART_HandleTypeDef`；
- `DMA_HandleTypeDef`；
- `HAL_StatusTypeDef`；
- STM32 IRQn；
- DMA Stream；
- HAL宏。

当前项目允许 Platform 仅提供 `.h` 接口定义。

------

## 10.4 Impl

Impl负责直接实现 Platform UART API。

STM32版本负责：

- HAL UART；
- DMA；
- IDLE；
- IRQ；
- HAL Callback；
- STM32错误处理。

例如：

```
platform_uart_send()
```

声明于：

```
Platform/platform_uart.h
```

实现于：

```
Impl/STM32/stm32_uart.c
```

------

## 10.5 Vendor

Vendor包括：

- STM32 HAL；
- CMSIS；
- CubeMX生成代码；
- FreeRTOS；
- RTT；
- EasyLogger；

等第三方或芯片厂商代码。

业务逻辑原则上不得直接修改 Vendor 源码。

------

# 11. 并发约束

## CON-001 RX所有权

DMA RX Buffer由 Impl 独占管理。

其他模块不得直接修改 DMA Buffer。

------

## CON-002 Ring Buffer所有权

RX Ring Buffer由 UART Service 管理。

APP不得直接修改 Ring Buffer 的：

- Read Index；
- Write Index；
- Buffer Memory。

------

## CON-003 ISR安全

ISR/Callback调用的函数必须明确是否支持 ISR Context。

不得在ISR中调用可能阻塞的 API。

------

## CON-004 共享状态

ISR和Task共享的变量必须考虑：

- 原子性；
- volatile使用场景；
- 临界区；
- RTOS同步机制；

禁止默认认为单条 C 语句天然线程安全。

------

# 12. 性能指标

以下指标作为第一版建议验收基线，后续根据实测调整。

### UART

建议测试配置：

- 波特率：115200 baud；
- 数据格式：8N1；
- DMA RX：开启；
- DMA TX：开启。

------

### Buffer

建议第一版：

DMA RX Buffer：

```
128 Byte
```

RX Ring Buffer：

```
1024 Byte
```

这些值属于测试基线，不属于不可修改的系统限制。

------

### 数据测试

系统至少应能够正确处理：

- 1 Byte；
- 小于 DMA Buffer 的数据；
- 等于 DMA Buffer 的数据；
- 大于 DMA Buffer 的数据；
- 1～256 Byte 随机长度数据；
- 连续无固定帧间隔数据。

------

### 连续运行

115200 baud 条件下连续通信至少：

```
60 s
```

应满足：

- 无HardFault；
- 无内存越界；
- 无异常死锁；
- 无非预期接收停止。

当处理能力足够且 Ring Buffer 未发生合法 Overflow 时：

```
dropped_bytes = 0
```

------

### 软件处理延迟

从 RX Event 到 UART Service Task 开始处理数据：

建议目标：

```
≤ 20 ms
```

实际值通过测试测量，而不是仅通过代码推断。

------

# 13. 可验收条件

项目第一阶段满足以下条件后视为核心功能完成。

## TEST-001 基本DMA RX

PC向STM32发送数据。

STM32能够通过：

UART
→ DMA
→ RX Event

正确获得数据。

------

## TEST-002 不定长数据

分别发送：

1 Byte
7 Byte
31 Byte
64 Byte
127 Byte
128 Byte
200 Byte
256 Byte

均能够正确接收。

------

## TEST-003 Ring Buffer

验证：

- 写入；
- 读取；
- Wrap Around；
- 空；
- 满；
- 部分写入；
- Overflow。

------

## TEST-004 DMA + Ring Buffer

连续发送多组不定长数据。

数据能够：

DMA Buffer
→ Ring Buffer
→ Service Task

正确转移。

最终数据内容和顺序必须与发送端一致。

------

## TEST-005 Overflow

主动降低 Consumer 处理速度，使 Ring Buffer 填满。

系统应：

- 不崩溃；
- 不越界；
- Overflow计数增加；
- Dropped Bytes正确增加；
- 后续通信能够继续。

------

## TEST-006 DMA TX

发送指定数据。

必须验证：

- 数据完整；
- 数据顺序正确；
- DMA完成事件正确；
- Busy状态有效。

------

## TEST-007 TX Busy

DMA发送尚未结束时再次发送。

系统应返回明确 BUSY，而不是破坏前一次数据。

------

## TEST-008 连续压力测试

随机长度数据连续发送至少60秒。

比较：

PC发送数据
STM32接收统计
实际读取数据

确认：

- 无非预期数据丢失；
- 无死锁；
- 无接收停止；
- 无HardFault。

------

## TEST-009 异常恢复

人为制造 UART 或 DMA 异常。

确认：

- 错误被记录；
- 软件能够重新进入正常接收状态；
- 不要求复位 MCU 才能恢复。

------

## TEST-010 日志隔离

开启大量 RTT + EasyLogger 日志。

业务 UART 数据中不得混入日志数据。

业务 UART TX DMA 不得被 EasyLogger 占用。

------

# 14. 第一阶段完成定义

本项目第一阶段完成标准不是“所有架构代码都完成”，而是以下完整数据链已经稳定运行：

UART硬件
→ DMA
→ IDLE/RX Event
→ Impl
→ Platform UART接口

同时：

RTT
→ EasyLogger

- 性能优化；
- API重构；

- 多UART；
- 更高级数据模型；

等后续扩展。
